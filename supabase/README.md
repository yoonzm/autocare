# Supabase 商户 V1

会员全店汇总已改为数据库聚合，部署顺序与统计口径见 [会员汇总说明](../docs/member-summary-integration.md)。后续高权限访问收敛、统一鉴权及跨店测试方案见 [权限收敛待实现方案](../docs/supabase-access-hardening-plan.md)，该权限重构尚未实施。

本目录包含商户注册/登录、服务项目、会员卡种、次卡套餐配置的数据库迁移和 `merchant-v1` Edge Function。所有业务写入和归属校验都在云函数中；客户端不持有 `service_role` 密钥。会员、订单等不在 V1 范围。

正式环境为私有化实例 `https://autocare.mymember.ltd`，由 `supabase-prod.yml` 在 `main` 自动部署，支持手动触发；详见 [`docs/release.md`](../docs/release.md)。App 与自动打包均使用正式环境，后续仅维护生产环境。正式部署只安装仓库结构与函数。

私有化部署的环境变量由 Docker Compose 提供，所有环境的短信和车牌识别均调用真实服务，不提供 mock 回退。保留网关的 API key 校验和现有函数运行时 JWT 校验；公开登录请求通过 publishable key 调用，受保护的业务动作继续由函数验证用户 JWT。`config.toml` 不会自动改变自托管运行时配置。凭证签名链接在返回 App 前映射为公网域名，避免客户端拿到内部 `api-gw:8000` 地址。

部署顺序：

1. 在目标项目执行版本化迁移，先在备份/测试环境验证。旧表如已有数据，迁移前必须人工审查，不能直接删除。正式环境通过生产部署流程执行迁移。
2. 部署 `functions/merchant-v1/index.ts` 为 `merchant-v1`。公共注册/登录动作需要关闭平台层 JWT 校验（`config.toml`），函数内部对所有业务动作自行验证访问令牌。
3. 配置助通真实短信渠道和按用途区分的模板，详见 [`docs/sms.md`](../docs/sms.md)。验证码随机生成 6 位，数据库仅存 HMAC-SHA256，5 分钟有效；同一手机号 60 秒一次、每天最多 10 次，全环境每天最多 200 次，错误最多 5 次。最终操作原子消费验证码。所有环境都通过短信交付验证码，没有短信 mock 配置或明文返回分支。
4. 客户端只使用项目 URL 与 publishable key。绝不将 `SUPABASE_SERVICE_ROLE_KEY` 下发到 App。

云函数按 `auth.ts`、`services.ts`、`cards.ts`、`shared.ts`、`types.ts`、`index.ts` 分模块，`types.ts` 定义动作及数据模型。已提供 `send_code`（同一手机号每天最多发 10 次，超限返回“今日发送次数已达上限”，按东八区自然日计）、`check_code`、`forgot_verify`（忘记密码第 1 步：验证码正确且该手机号是已开通门店的账号）、`reset_password`（第 2 步：再次校验验证码并设置新密码，随后让该账号的全部会话失效，所有设备都要重新登录）、`register`（保存城市、地址、联系人、身份、工位数量、主营业务，开通 14 天试用，并给新门店初始化设计稿里的示例数据：按所选主营业务生成设计稿的服务项目（洗车美容 → 洗车 + 内饰，镀晶镀膜 → 镀晶镀膜，隐形车衣 → 贴膜；设计稿没有改色膜、保养维修的示例，只选这两项时服务项目为空；默认三项共 10 个，含次卡套餐需要的镀晶养护、空调杀菌），以及黑金卡、金卡、银卡、普通会员 4 个卡种，还有设计稿的次卡套餐（只创建所含服务已存在的，见 `defaults.ts` 的 `defaultPackages`）；任何一步失败都会整体回滚，不留半成品门店；数据定义在 `defaults.ts`，店主之后自行修改）、`login_password`、`get_store`（读取当前门店资料）、`change_password`（校验当前密码）、`change_phone`（当前号码与新号码两个验证码）、`delete_account`（进入 15 天注销冷静期，期间重新登录即撤销；到期清除的定时任务仍为 `TODO`）、`login_code`（验证码登录：校验一次性验证码、确认手机号已注册后签发会话）、`list/save/delete`（服务项目与卡种）、卡种的 `rules` / `save_rules`（门店通用规则）接口；卡种 `save` 还保存卡面颜色、升级条件、积分倍率、生日礼、预约优先、有效期。服务项目删除为物理删除；卡种因既有界面文案为“停用”，`delete` 开发时执行 `cd supabase/functions/merchant-v1 && deno task check` 检查模块类型。Dashboard 部署须同时包含入口及其依赖模块；`types.ts` 是编译期类型文件，不含运行时代码。

预约管理（`202611030002_appointments.sql`，`appointments.ts` / `appointment_rules.ts`）新增 `appointment_*` 动作：`board`（`day` 所在周）、`get`（`id`）、`options`（设置、服务、资源）、`summary`（首页今日待到店）、`slots`（`day`、`service_ids`、可选 `exclude` / `bay_id` / `technician_id`）、`save`（新建：`member_id?` / `service_ids` / `starts_at` / `bay_id?` / `technician_id?` / `note`；改期：`id` / `starts_at` / 资源 ID）、`arrive` / `cancel`（取消带 `reason`）、`checkout`（`id`、收银项目与方式）、`settings_save`、`resource_save`（工位；技师改由 `staff_save` 维护，见 `docs/staff-integration.md`）。接口不接受客户端指定门店、报价或占用时长。标准工时由服务项目保存，默认 30 分钟；时间冲突、容量、归属和状态变化在云函数及数据库事务中执行。先迁移再部署，SQL 断言用 `supabase/tests/appointments.sql`。员工登录激活、微信短信、定金、个人休假、额外节假日和预约挂单暂未接通，详见 `docs/backend-integration.md`。

注册开通试用时，云函数还会按商家选择的工位区间初始化真实工位：`1-3 个` 创建 3 个、`4-6 个` 创建 6 个、`7-10 个` 创建 10 个、`10 个以上` 创建 20 个，按“1 号工位”起顺序命名。工位创建失败与其他初始化失败一样会删除新建账号及门店，不返回开通成功；既有门店不自动补建。

注册还会按主营业务创建可编辑的库存商品资料（`defaults.ts` 的 `defaultProducts`）：多选去重，库存、安全库存和成本均为 0，不创建虚构的入库流水；保养维修商品暂归现有“配件”分类。库存商品初始化失败同样不能返回开通成功，既有门店不自动补建。

公共地区字典（`202611060003_regions.sql`）：`action=regions` 在注册前可读取完整三级字典，传 `version` 支持未修改响应。注册选择省、市两级，提交 `province_code` / `city_code`，云函数校验有效状态与父子关系，生成 `city` 文本。旧门店文本保持原样，编码不猜测回填。来源、数据年份、特殊层级和后续更新方式见 [数据说明](data/regions/README.md)。先迁移，再部署云函数，再发布客户端；旧客户端缺少编码，不能继续通过注册校验。回归验证：`deno test region_rules.test.ts`、`supabase/tests/regions.sql`、Flutter `region_picker_test.dart` / `account_test.dart`。生成页面、注册表单结构和两列滚轮布局不变；地区数据及注册编码校验已接通，短信沿用主分支现有的真实短信服务。

会员端小程序使用独立的 `member-v1` 云函数（`functions/member-v1`，`mb_*` 动作，会员会话令牌鉴权），与 `merchant-v1`、`admin-v1` 共享数据库；说明与部署顺序见 [`docs/member-mini-integration.md`](../docs/member-mini-integration.md)。检查：`cd supabase/functions/member-v1 && deno task check && deno test`。

「我的 · 编辑资料」（迁移 `202611100005_profile_edit.sql`，`account.ts`）：`profile_update`（`name`、`email`）经 `merchant_profile_update` 保存当前登录身份自己的资料——老板写入账号下所有门店的联系人姓名和账号邮箱，员工只改自己的员工档案；`get_store` 另返回 `profile`（姓名、邮箱、角色、手机号、入职/开通日期）。头像（迁移 `202611100006_profile_avatar.sql`）：`profile_avatar_upload`（`data` 为 JPEG/PNG 的 Base64，≤5MB，服务端按文件头校验）上传到私有桶 `profile-avatars`，经 `merchant_profile_set_avatar` 原子记录到当前身份并清理旧文件；`profile.avatar_url` 为 1 小时有效的签名链接。客户端选图后只本地预览，点保存时先上传再保存资料。手机号更换沿用「账号与安全」。先迁移再部署云函数。

后台「短信记录」（迁移 `202611100007_sms_logs.sql`，`admin-v1/sms_logs.ts`）：每次验证码短信在预留时写入 `sms_logs`（手机号、用途、验证码明文、短信内容、通道与签名），发送结束记录“已发送 / 失败”及原因，校验时同步错误次数与是否已使用；按产品决定验证码明文保存、手机号不脱敏，因此只有超级管理员能读：`sms_list`（`kind` = all/code/notice/failed、`phone`、`before` 游标、`limit`）、`sms_get`（读取详情并写入审计 `sms_view`）、`sms_resend`（只对验证码短信，按原用途生成新验证码并经真实渠道发送，写审计 `sms_resend`），权限在云函数与 SQL 双重校验。“通知”类短信目前系统不发送，列表为空，表结构已预留 `kind='notice'`。渠道只返回“已受理”，没有送达回执，页面显示“已发送”，送达时间留空，对应 `TODO sms_delivery_receipt`；短信内容按签名与验证码拼出，不是渠道模板原文；验证码明文没有定时清理，对应 `TODO sms_log_cleanup`。先迁移再部署云函数。测试：`supabase/tests/sms_logs.mjs`、`admin-v1` 的 `handler.test.ts`。

后台「用户账号」（迁移 `202611100008_account_cancellation.sql`，`admin-v1/users.ts`）：账号 = 一个登录用户（老板有门店账号，员工有门店身份，可同时有多个身份，运营账号不在其中）。`user_list`（`status` = all/cooling/cancelled/frozen、`q` 手机号/姓名/门店名、`before` 游标、`limit`，同时返回各状态数量）、`user_get`（身份、在线设备数、进行中的挂单与待到店预约数、操作记录）、`user_cancel`（强制注销，`id`、`reason` = user_request/violation/other、`note`，`X-Request-Id` 幂等）。**注销只处理账号**：写入 `account_cancellations`、删除该用户的全部登录会话（所有设备退出）、写审计 `user_cancel`，随后在云函数里封禁登录（`ban_duration`）；`merchant-v1` 的验证码登录、密码登录和发验证码前也会拒绝已注销账号。不删除、不改动门店、订单、会员等任何数据；已注销用户绑定过的员工身份不能再被同一手机号（含注销后新建的用户）顶替登录（迁移 `202611120002_cancelled_staff_login.sql`，登录判断、身份列表、选择身份、会话校验均过滤），用户自助注销（进入 15 天冷静期、所有设备退出）同样只处理账号。三个动作只有超级管理员能用，云函数与 SQL 双重校验。冻结账号本期未实现，后台页面明确提示未接通（`TODO account_freeze`，预期接口 `user_freeze`）；冷静期到期后的自动注销仍缺定时任务（`TODO account_cancel_expired`），到期不会自动生效。先迁移再部署云函数。测试：`supabase/tests/account_cancellation.mjs`、`admin-v1` 的 `handler.test.ts`。
