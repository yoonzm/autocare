# 前端规范

适用于商家端、后台端 Flutter App；会员端、员工端小程序按同一规则落地。来源是设计稿「前端加载与反馈规范」分页（SPEC 01–06 与手机端场景示例）。

任何会等待网络的界面，都要回答四个问题：**等的时候看到什么？失败了怎么办？没数据怎么办？用户能不能重复点？**

商户 App 已进入源码迭代阶段，停止从设计稿生成代码；页面维护与历史生成代码迁移统一遵循第 18 节。设计稿保留为视觉参考。

> 这套规范经用户明确要求落地，属于对既有界面的批准变更（`AGENTS.md` 要求改界面前先取得同意）。除本规范明确规定的加载 / 空 / 错误 / 提交状态外，其他页面结构、文案、样式不变。

## 1. 加载时序

| 耗时 | 表现 |
| --- | --- |
| 0 – 300ms | 不显示任何指示，保持原有内容或空白背景，快速返回的请求不闪烁 |
| ≥ 300ms | 按场景出现加载态：结构固定的首次内容加载可用骨架屏；结构不固定或非首次加载用局部 spinner / 进度指示；按钮用按钮内 spinner |
| 最短 500ms | 加载指示一旦出现，至少停留 500ms，避免一闪而过 |
| ≥ 10s | 提示“网络较慢”；阻断式操作此时出现“取消” |
| 15s | 普通请求超时（上传、导出 60s），进入错误态并可重试 |

## 2. 场景与方案

| 场景 | 加载表现 | 要点 |
| --- | --- | --- |
| 页面首次进入 | 结构固定且预计超过 300ms 时用骨架屏 | 只覆盖内容区，与真实布局一致；表单等不适用场景直接显示页面壳层和可用内容 |
| 下拉刷新 | 顶部刷新指示器 | 内容不清空；完成后提示“已更新” |
| 上拉加载更多 | 列表底部 footer | 加载中 / 没有更多了 / 失败点击重试 |
| 按钮提交 | 按钮内 spinner + “提交中…” | 宽高不变；加载期间禁用，防连点 |
| 阻断式操作（支付、导出） | 全屏遮罩 HUD | 仅限必须等待的操作；10s 后可取消 |
| 切换 Tab / 筛选条件 | 保留旧内容 + 顶部细进度条 | 不整页白屏；内容区降到 60% 透明度 |
| 搜索 | 防抖 300ms + 输入框内 spinner | 保留已有结果；结果区结构不固定时用普通 loading，不整页换骨架；无结果走空数据 |
| 图片 / 头像 | 灰色占位 → 150ms 淡入 | 失败显示占位图，点击重试；头像失败显示首字 |
| 上传 / 导出 | 进度条 + 百分比 | 可取消；失败可重试且保留已选文件 |

### 骨架屏的适用边界

- **适用**：首次进入且尚无可展示数据、内容结构固定、加载时间略长（约超过 300ms）的列表、详情、首页 / 看板卡片、信息流 / 卡片流。列表项应同构；详情页按头部、信息卡片、记录区占位；看板按独立卡片区块占位。
- **不适用**：无预填数据的新建表单、改密码等表单；提交、支付、导出等操作；预计 300ms 内完成的请求；搜索结果等结构或高度差异大的内容；下拉刷新、加载更多；空数据与失败状态。编辑表单如需等待预填数据，仅对待填充字段区占位，保留表单壳层和已可用控件。
- **时序**：骨架仅用于首次无数据加载。先延迟 200–300ms（当前统一组件为 300ms）再显示，避免闪烁；一旦出现，遵循最短展示 500ms。已有数据时刷新、筛选或切换条件要保留旧内容，不能退回骨架；无旧数据的错误重试使用错误态按钮 loading，不反复显示骨架。
- **形状**：占位必须对应最终内容的层级、宽高、圆角和间距；头像用圆形，文字行按真实长短错落，卡片按真实圆角。不同结构不能仅因都是列表就套同一个通用 `SkeletonList`。同类列表的行数应一致，行数也要与可见区域和实际布局相称。
- **动效与切换**：只用轻微 shimmer；系统开启“减少动态效果”时显示静态灰块。加载失败立即切到错误态，成功且为空切到空状态，不让骨架一直播放。标题栏、底部导航等固定壳层从一开始就显示，只对内容区使用骨架。

## 3. 数据视图的六种状态

每个会请求数据的区块都要覆盖：

1. **加载中**：没有旧数据的首次进入，符合上面适用边界才显示骨架屏；否则使用对应的普通加载态。外壳（标题栏、底栏）保持不变。
2. **有数据**：内容以 150ms 淡入替换骨架，布局不跳动。
3. **无数据**：请求成功但为空，按原因展示空状态与下一步动作。
4. **加载失败**：没有旧数据时，整页错误态 + 重试按钮。
5. **刷新中**：已有数据时的下拉刷新、筛选，旧内容保留，只在顶部提示。
6. **刷新失败**：有旧数据时只弹 Toast（可重试），不替换页面内容。

## 4. 异常状态与重试

按错误类型给出固定文案和动作。能重试的一律给“重试”；不能重试的给明确的下一步，不让用户停在死页面。

| 类型 | 触发 | 标题 / 说明 | 动作 |
| --- | --- | --- | --- |
| 网络异常 | 无网络连接 | 网络不太给力 · 请检查网络设置后重试 | 重试；恢复网络时自动重新请求一次 |
| 请求超时 | 15 秒无响应 | 请求超时 · 当前网络较慢，请稍后重试 | GET 先静默重试 1 次（间隔 1s），仍失败才展示 |
| 服务异常 | 服务端 5xx | 服务开小差了 · 我们正在处理，请稍后再试 | 重试；底部小字展示错误码（如 `SRV_503`），长按可复制 |
| 登录失效 | 401 / 令牌过期 | 登录已过期 · 请重新登录后继续使用 | 先静默刷新令牌，失败才提示；登录后回到原页面，不丢草稿 |
| 无权限 | 403 | 暂无权限访问 · 请联系店主在“角色权限”中开通 | 只给“返回”，不提供重试 |
| 内容不存在 | 404 / 已删除 | 内容不存在或已删除 · 返回上一页看看其他内容 | 只给“返回”；从列表进入详情后被删除，返回列表并静默刷新 |

- 有旧数据时：刷新失败只弹 Toast（可重试），不用整页错误态覆盖已有内容。
- **业务失败（4xx 业务码）**：直接展示服务端文案，表单类显示在字段下方，其他类用 Toast，不套用上面的整页状态。
- 因此只有 **401** 视为登录失效；带服务端文案的 403 / 404（如“当前密码错误”“该手机号尚未注册”）按业务失败处理。登录、注册类接口的 401 是“账号或密码错误”，不触发刷新令牌 / 登录失效。

## 5. 空数据

请求成功但没有数据，要说清“为什么空”并给出下一步。三要素：**图标 + 一句话说明 + 下一步动作（可选）**。空状态不等于失败，两者不能混用同一套视觉。

| 类型 | 示例 | 动作 |
| --- | --- | --- |
| 首次为空 · 引导新建 | 还没有会员 | 主按钮“添加会员”，可附次要入口 |
| 搜索无结果 | 没有找到“沪A8K”相关结果 | 只给“清除搜索”，不引导新建；回显用户输入的关键词 |
| 筛选无结果 | 当前筛选下没有数据 | “重置筛选”；筛选条保持可见，可直接改条件 |
| 已清零 · 正向反馈 | 待办已清零 | 绿色、轻松语气，不放按钮 |
| 功能未开通 · 引导升级 | 当前套餐不含“数据备份” | “查看套餐”；这是权限提示，放在功能入口处而非空列表里 |
| 局部为空 · 轻量提示 | 跟进记录 暂无跟进记录 去添加 | 卡片、分区内只用一行文字，不用大图标 |

- 空状态仍可下拉刷新，并保留页头和搜索栏；不要把整页替换成一张图。
- 文案口吻：陈述事实 + 给出出路，不用“暂无数据”这类空泛说法；不责怪用户。
- 能新建数据的页面首次为空才放新建按钮，只读类页面不放。各页面的类型、标题、按钮见设计稿“空状态 · 各页面对照表”（商家端、会员端、员工端、后台端四张表）。

## 6. 按钮提交

所有会发请求的按钮都要有“加载中”。点击后立即进入 loading，请求期间禁用，结束后进入成功态或恢复可点，不能让用户猜“点上了没有”。

- 点击后 100ms 内必须有反应：按压态 80ms，loading 立即出现。
- loading 时宽高不变，文案由“提交”变“提交中…”，不引起布局抖动。
- loading 期间忽略重复点击；写请求带同一个幂等标识（`X-Request-Id`），防止重复下单、重复充值。
- 成功态停留 1s 后自动跳转或恢复，文案变成结果（“已保存”）。
- 失败后按钮恢复可点，表单内容保留，用 Toast 说明原因，不清空输入。
- 点击区域不小于 44×44pt；禁用态要说明原因（如“请先填写手机号”），不能只置灰。
- 验证码按钮：发送中显示“发送中…”，成功后倒计时 60s（期间不可点）；失败立即恢复。
- 图标按钮：图标位置直接替换为 spinner，尺寸不变。行内小按钮（如错误态的“重试”）同样要有 loading。
- 危险操作二次确认；**确认按钮自带 loading，完成后再关闭弹层**；失败时弹层保持打开。

### 加载态的通用要求（曾经出现过的问题，不允许再出现）

**2026-11-13 按钮标准化补充（用户明确批准，优先于下列旧按钮外观约定）**：商户端普通 / 图标按钮全部采用 `packages/ui_kit` 标准外观、尺寸、颜色与交互，无需还原旧样式。普通按钮保留原文案、左侧显示内置 16px 转圈，提前预留加载宽度；顶部保存按钮不再收缩成圆。图标按钮隐藏图标、显示 20px `AppSpinner`，保留背景与尺寸。`ActionButton` 只适配既有 `busyActions`，`RequestButton` 复用统一异步动作；业务提交、防重复、错误与实例隔离仍保留。

验证码统一使用纯展示的 `AppSmsCodeButton`：宽 132、视觉高 36、热区高 44，可发送 / 发送中 / 倒计时 / 重发四态。继续复用页面持有的 `SmsCodeController`、真实短信请求与错误处理；组件不计时、不请求后端。发送中使用 16px `AppSpinner`，发送 / 倒计时禁点，失败恢复可发送。下列第 4、8 条中旧普通按钮的 spinner 及“提交中…”文案规则，以此标准组件表现为准；非按钮加载规范仍有效。

既有加载按钮和部分骨架行为有自动测试（`test/busy_ui_test.dart` 等）；骨架与真实页面的形状匹配仍需逐页视觉核对。新增页面或按钮时按此检查。

1. **骨架屏贴着内容区域顶部、占满区域**，不能被居中而在上方留一大块空白（`AsyncView` 的切换动画默认是居中布局，必须用顶部对齐的 `layoutBuilder`）。
2. **同类列表的骨架行数一致，形状优先匹配真实布局**：现有服务项目、会员卡种等列表暂以 5 行作为行数基线；新增列表先核对真实行结构和可见高度，不能直接把通用 `SkeletonList(count: 5)` 用在不同样式的列表、详情或表单上。
3. **按钮 loading 不能改变按钮的宽、高、形状**：不允许出现底部通栏按钮缩成小圆、文字和转圈叠在一起这类变形。实现上用 `StackFit.passthrough` 沿用外层约束，转圈用 `Positioned.fill` 画在原内容位置，不参与布局。所有页面统一用 `hBusy` / `LoadingButton` / `PrimaryButton(loading:)`，不要各页自己叠转圈。
4. **loading 时原内容（文字 / 图标）隐藏，只显示转圈**，不能和转圈叠加。全宽底栏按钮（高度 ≥ 48）按设计稿显示“转圈（18）+ 提交中…”，转圈在左、文字在右、整体居中，按钮尺寸不变；右上角的“保存”胶囊按钮按设计稿的图标按钮样式：加载时变成 44×44 的圆，里面只放 20px 转圈（不显示文字），结束后恢复；图标按钮同样只转圈、尺寸不变。正式维护的源码用 `PrimaryButton` / `LoadingButton` 等统一按钮，显式配置加载表现；历史页面迁移时保留原有按钮外观。
5. **图标按钮 loading 只显示转圈（20px、主色），不显示原来的图标**，按钮尺寸不变。
6. **同一个动作的其他按钮不转圈**：保存页点“保存”时，只有“保存”转圈，左上角取消 ✕ / 返回只是不可点，不能也转圈。
7. **验证码按钮点击后立即有加载效果**：转圈（16）+“发送中…”，灰色，期间不可再点；失败立即恢复“获取验证码”，成功后进入 60 秒倒计时。加载指示至少停留 500ms。
8. **统一转圈样式**：全部使用 `AppSpinner`（淡色圆环 + 1/4 圆弧，0.8s 一圈，开启“减少动态效果”时不转），尺寸按设计稿：图标按钮 20、主要按钮 18、验证码按钮 16、行内小按钮 14。不要直接用 `CircularProgressIndicator`。
9. **提交按钮显式绑定异步回调与加载状态**，按第 18 节维护。生成脚本及其 `ASYNC_ACTIONS` 已移除；`asyncActionKeys` 仅为未迁移页面保留兼容，不再新增业务动作。测试直接检查兼容键对应的实际 loading 控件；迁移时清理旧键，保留未迁移页面的检查。页面动作清单不进入共享 UI 包。

## 7. 反馈组件

全 App 只用这一套，不各页自己画。

- **Toast**：成功 3s、失败 5s（带操作 8s）；同一时刻最多 1 条，新的替换旧的；不被键盘和底栏遮挡。
- **网络状态条**：离线条常驻页面顶部、推开内容；恢复后变绿，2s 后消失并自动刷新。离线时写操作按钮禁用并说明原因。
- **全屏遮罩 HUD**：拦截所有点击，仅用于支付、导出这类必须等待的操作；10s 后出现“取消”。能用按钮 loading 的不用遮罩。
- **进度**：顶部细进度条用于切换 Tab / 筛选；能估算进度用确定进度，否则用不确定进度。
- **下拉刷新**：阈值 64px，越过时轻触觉；完成提示停留 1s；刷新中不可再次触发。
- **列表底部 footer**：加载中… / — 没有更多了 — / 加载失败，点击重试；距底部 200px 预加载；首屏不足一屏时不显示“没有更多了”；与下拉刷新互斥。
- **骨架元素**：轻微闪光 1.4s 循环；尺寸、圆角、间距与真实内容一致；开启“减少动态效果”时改为静态灰块。只在符合“骨架屏的适用边界”的首次无数据加载使用。

## 8. 表单输入

- **所有表单输入框没值时都必须有 placeholder**（不论是否带默认值——用户清空后看到的就是 placeholder）。
  - 文案：设计稿写了就用设计稿的；没写的用输入框对应的标签文字拼成“请输入××”（如标签“项目名称” → “请输入项目名称”），不用空泛的“请输入”。
  - 在正式维护的页面源码中显式填写 `hintText`；历史生成页需要修改时按第 18 节迁移，不再通过生成器补齐。
  - `test/placeholder_test.dart` 检查页面与弹层的 placeholder；迁移时同步更新扫描范围，不能通过移出 `gen/` 逃过检查。
- 提交前先校验；新页面的错误显示在字段下方，并滚动聚焦到第一个错误。历史生成页面及其迁移版本保留现有 Toast 校验反馈，避免借源码迁移改变布局；后续统一为字段错误提示时需单独确认视觉变更。已有字段错误提示的页面（如登录页）保持不变。
- 提交中整个表单只读，按钮 loading，防重复提交。
- 有未保存的修改时按返回，弹窗确认是否放弃。
- 键盘弹出时底部按钮上移；点击空白处收起键盘。
- 搜索框防抖 300ms；清除按钮一键清空并恢复完整列表。
- 密码框右侧的小眼睛必须可点击切换明文 / 密文。

## 9. 交互细节清单

评审页面时按清单逐条过。

**请求与重试**
- 超时：普通请求 15s，上传、导出 60s。
- 自动重试：GET 静默重试 1 次（间隔 1s）；POST 等写请求不自动重试。
- 手动重试：点击后立即进入 loading，期间不可再点。
- 多区块页面各自处理状态，一个区块失败不影响其他区块。
- 离开页面时取消未完成的请求，避免回调更新已销毁的页面。
- 乐观更新（开关、收藏）：先改界面，失败回滚并用 Toast 说明。

**列表与分页**
- 每页 20 条，滚到距底部 200px 时预加载下一页。
- 下拉刷新与加载更多互斥；刷新完成保持滚动位置；切换 Tab 后恢复各自的滚动位置。
- 末页显示“没有更多了”；首屏不足一屏时不显示。
- 新增、删除后局部更新对应条目，不整页刷新。

**网络**
- 离线：顶部常驻提示条，写操作禁用并说明原因；恢复后自动刷新。
- 弱网：超过 10s 提示“网络较慢”，阻断式操作可取消。

**页面生命周期**
- App 回到前台超过 5 分钟，静默刷新当前页，不弹骨架。
- 底部 Tab 切换保留各页状态，不重复请求；详情页修改后返回列表，只更新对应条目。
- 弹层、底部抽屉里的请求，关闭弹层时取消。

**动效与无障碍**
- 内容替换骨架用 150ms 淡入；按压反馈 80ms 内出现；深色模式下骨架和遮罩同步换色。
- 加载区域标记为忙碌，状态变化用无障碍播报（“加载中”“已加载完成”“加载失败”）。
- 可点区域不小于 44×44pt；状态不只靠颜色传达，错误同时有图标和文字。

## 10. Flutter 落地约定

统一组件放在 `apps/merchant/lib/kit/async_kit.dart`，页面不再各自写加载和错误处理：

| 组件 | 用途 |
| --- | --- |
| `AsyncView<T>` | 包装请求，按状态渲染 骨架 / 内容 / 空 / 错误；自带 300ms 延迟、500ms 最短展示、150ms 淡入、刷新失败 Toast |
| `LoadingButton` | `onPressed` 返回 `Future`，自动 loading、防连点、失败 Toast、可选成功态 |
| `AppSkeleton` / `SkeletonList` | 闪光骨架元素；`SkeletonList` 仅适用于行结构匹配的列表，其他页面应组合 `AppSkeleton` 贴合真实布局 |
| `EmptyView` | 图标 + 标题 + 说明 + 可选动作（`firstTime` / `filtered` 等） |
| `ErrorView` | 按错误类型出文案，带 `onRetry`（重试中按钮 loading） |
| `AppToast` | success / error / info / loading，同一时刻最多一条 |
| `runBusy` / `BusyOverlay` | 历史页面的兼容加载机制；原有键为 `当前页>目标页`，登记在 `asyncActionKeys`。迁移后改为显式异步回调与按钮加载状态，见第 18 节 |
| `AppError` | 统一错误类型：network / timeout / server / auth / forbidden / notFound / business |

**网络层约定**（`lib/backend/merchant_api.dart`）
- 统一超时 15s；上传、导出 60s。
- 所有响应统一映射为 `AppError`。
- GET 类读请求（`list` / `get_store` / `check_code`）失败静默重试 1 次，写请求不自动重试。
- 401 先静默刷新令牌，失败再通知 App 回到登录页（`authExpired`）。登录 / 注册类接口的 401 是业务失败，不走这条。
- 写请求带 `X-Request-Id` 作为幂等键。
- 页面销毁后返回的结果直接丢弃（Dart 的 `Future` 不能真正取消），不更新已销毁的页面。

## 12. 单选标签（ChoiceChip）

## 13. 数字增减控件（NumberStepper）

2026-11-13 按钮迁移补充：用户已批准数字增减按钮采用 `AppIconButton.small` 标准外观及热区；`HNumberStepper` 继续统一处理数值、步长与回调，不再接收自定义 `minus` / `plus` 外观插槽。以下历史“保留按钮外观”的描述以此补充为准，数值格式、边界与业务行为仍保持。

适用于预约设置、库存出入库、门店设置、卡种编辑、服务选择等用「减号 / 数值 / 加号」调整数字的场景。统一使用 `lib/kit/kit.dart` 的 `HNumberStepper`，不要在页面里分别拼接三个按钮并各自处理增减。

- 组件接收同一个 `ValCtrl`、正数 `step`，以及设计稿对应的减号按钮、数值区、加号按钮；点击逻辑由组件统一处理。`step` 使用控制器存储单位：整数按 1 或设计稿指定步长，小数按放大后的整数步长。
- 中间数值由 `hCount` 监听并按原小数位、单位后缀与千分位格式显示；值变化应立即回显。`ValCtrl.add` 的默认下限为 0，不能出现负数；具体业务上限、价格、权益仍由后端校验。
- 复用的是交互与布局骨架，不强行统一不同设计稿的颜色、图标、圆角、宽高和间距。替换前后须保持页面原有外观、可点击范围、数值格式及步长。组件为增减按钮提供「减少」「增加」无障碍标签。
- 预约设置的六处数字控件统一通过 `_BookingNumberStepper` 保留 32px 圆形按钮和原有 SVG；其他页面直接在正式源码中使用 `HNumberStepper`。历史生成页按第 18 节迁移，不再运行生成器或 `--rewrite-existing` 更新文件。
- 验收：增减一次只触发一次变化；下限不越界；所有数量、金额与折扣的单位、步长、小数位不变；页面视觉和关键流程不变。

## 14. 基础组件库（全局维护一份）

> 本节说的是商户端 `lib/kit/` 里的组件。共享的 `packages/ui_kit` 组件库的使用规则见第 17 节，两者并存，以各页面设计稿为准。

商家端和后台端共用的加载、错误、空态、Toast、按钮 loading 在 `packages/async_kit/lib/src/` 按职责实现，`lib/async_kit.dart` 仅作公共导出入口。商家原路径 `lib/kit/async_kit.dart` 保留 export 兼容；后台直接依赖共享包。修复通用行为只修改共享实现，不在两端复制组件。

- 共享包不包含商户路由清单、服务/卡种等业务页面模板、完整应用主题或 Supabase SDK。商户专用骨架放 `apps/merchant/lib/widgets/loading_skeletons.dart`，动作清单放 `apps/merchant/lib/kit/async_action_keys.dart`。
- 共用组件从当前 `Theme` 的 `AsyncKitTheme` 扩展读取反馈所需颜色及权限提示；两端各自维护完整主题。禁止用同步两份全局 `C.dark` 的方式驱动共享组件，禁止在共享层写入“联系店主”等应用语义。
- Supabase 异常在各端 API 边界通过 `packages/supabase_adapter` 转成通用 `AppError`；UI 只处理通用错误，不直接识别 SDK 异常。

分段条、单选 / 多选标签、数字增减、开关、骨架屏、空 / 错误态、按钮 loading、选择器、颜色选择等**基础组件只在组件库里实现一份**，所有页面引用，不在页面、模板或绑定层里各自重写、复制一份“长得差不多”的版本。

- **位置**：通用交互与布局组件放 `lib/kit/`（`async_kit.dart`、`kit.dart`、`pickers.dart`、`color_picker.dart` 等）；带业务语义的复合组件放 `lib/widgets/`。新增基础组件先在组件库里实现并写测试，再被页面引用。
- **先找后写**：需要某个控件前，先在 `lib/kit/`、`lib/widgets/` 里找有没有；有就复用，没有就先补进组件库，不要直接写在页面文件里。页面内只允许放只在该页使用、不可能复用的纯布局。
- **不复制改样式**：不同设计稿的颜色、尺寸、圆角、图标通过参数、插槽（如 `on` / `off`、`minus` / `plus`）传入，交互和状态逻辑留在组件内。发现两处实现了同一个控件，要合并成一份，而不是再加第三份。
- **骨架 / 加载 / 空 / 错误态同理**：页面骨架用 `AppSkeleton` 组合出与真实布局一致的形状；固定外壳（标题栏、返回、右上角操作）用组件库的 `AppPageHeader` / `AppHeaderAction`（`lib/kit/page_header.dart`），骨架里直接显示真实标题栏，不再自己画返回键和标题。
- **修缺陷改一处**：组件有问题（样式、状态、无障碍）在组件库里改，页面自动跟着修复；不允许在页面里打补丁绕开。历史生成页需要改动时按第 18 节迁移，在正式源码中引用组件。
- **验收**：新增 / 修改基础组件要覆盖选中、未选中、禁用、加载、深色模式，并检查依赖它的页面；PR 里列出复用的组件和新增到组件库的组件。

## 15. 表单页的出场方式（iOS 整页 sheet）

**左上角是关闭按钮（✕）的页面，一律以 iOS 整页 sheet 出场**：从底部滑入，顶部露出上一页，手势下拉可以关闭，和新增会员一致。

- **统一入口**：只用 `lib/kit/sheet_route.dart` 的 `appSheetRoute`（底层是 `CupertinoSheetRoute`），不在页面里自己 new 路由或另写一套下拉关闭。生成页由 `lib/routes.dart` 的 `_cupertinoSheetPages` 名单统一打开；手写页、绑定层里直接 `Navigator.push` 的入口也要用 `appSheetRoute`。新增 ✕ 页面时，把页面名加进 `_cupertinoSheetPages`。
- **上一页不缩放**：必须显式传顶部间距（`topGap: 0.08`），Flutter 在自定义顶部间距时不会让下层页面缩小。不要去掉。测试 `test/sheet_route_test.dart` 会检查上一页位置不变。
- **下拉手势**：页面里的滚动区域使用 sheet 提供的滚动控制器（`appSheetRoute` 已用 `PrimaryScrollController` 包好），滚到顶后继续下拉才关闭。页面内不要再给最外层滚动区域单独指定 `controller` / `primary: false`。
- **未保存的修改**：页面用 `ConfirmDiscard` 拦截返回时，下拉不会直接关闭，要点 ✕ 走“放弃未保存的修改？”确认，避免下拉误丢草稿。
- **不使用的情况**：
  - 结果页（支付成功、开卡成功、套餐售出、绑定完成、开通成功等，见 `resultPages`）：设计稿要求禁止下拉返回，保持原样。
  - 相机扫描页（扫码找会员、扫描行驶证 / 车牌）：全屏相机，保持从底部滑入的全屏页。
  - 左上角是返回箭头（<）的页面（详情、列表、编辑工位等）：保持原来的右侧推入。
  - 已经是底部弹层的界面（选择会员 / 服务、挂单、主题等）：沿用 `showModalBottomSheet`。
- **测试注意**：整页 sheet 下方的上一页仍在组件树里，单测里没有 `ToastHost` 时提示会出现两份 SnackBar，断言用 `findsWidgets` 或相应数量。

## 16. 按钮层级与位置

来源：设计稿 `SpecButtonLevels`。同一种作用，所有页面用同一种按钮；**颜色只表示“重要程度”，不表示“属于哪个功能”**。

| 层级 | 样式 | 用于 |
| --- | --- | --- |
| 1 主要 | 蓝色实心 `#0485F7`，白字。一个页面只有一个 | 新增、保存、提交、确认收款、下一步、完成 |
| 2 次要 | 白底（页面上）或灰底 `#EEEEF0`（底部栏、弹层里），深色字。可以有多个 | 筛选、导出、更多、开支、预算、编辑、取消、上一步、暂存、草稿、继续开单 |
| 3 文字按钮 | 无底色，蓝色文字。只用在内容里面和卡片内，**不放在页面右上角** | 修改、去修改、编辑权限等卡片内的链接式操作 |
| 4 危险 | 浅红底 `#FFE1E2`，红字 `#A43433`。只用于不能撤销的操作，且要二次确认 | 删除、退款、取消预约、注销 |

| 位置 | 规则 |
| --- | --- |
| 页面右上角（44px） | 主要：蓝色实心胶囊（保存）或蓝色圆形图标按钮（新增员工 +）。次要：白底胶囊或白底圆形图标（筛选、预算、编辑）。**不用纯文字**，包括“保存”“编辑”“预算” |
| 页面底部操作栏 | 主要放右侧，宽度比例 1.5–1.6；次要放左侧，灰底。一个页面最多一个主要 |
| 弹层底部 | 取消用灰底，确定用蓝色；确认破坏性操作时，确定改成浅红底红字（取消 + 确认退款） |
| 表单页保存 | **只放一处**：有底部操作栏的页面，保存放底部，右上角不再重复（预约设置、记一笔、编辑预算、总预算）；没有底部栏的表单页，保存放右上角（编辑工位、营业时间、会员资料、个人资料等） |

**不要这样做**
- 黑色实心不再用作按钮色（深色模式里的深色控件除外），黑色只用在深色卡片背景上。
- 同一页面不要同时出现两个蓝色主要按钮。
- 页面右上角不要放纯文字按钮。
- 不要用蓝色描边加白底做按钮，描边只用在“选中的标签”上。

**落地**
- 页面与绑定层新增或修改按钮时，先对照上表选层级，再复用 `PrimaryButton` / `LoadingButton` / `AppHeaderAction`（`lib/kit/`）；历史生成页按第 18 节迁移后维护源码，不再从设计稿生成。
- 主要按钮在深色模式下同样是蓝底白字，不随主题反色。
- 按钮 loading 的尺寸、转圈规则仍按“加载态的通用要求”。

## 17. 基础组件库 `autocare_ui_kit` 的使用规范

`packages/ui_kit`（`autocare_ui_kit`）是按设计稿「组件库」画板实现的基础组件库：令牌 `AppTokens`、按钮、选择标签、输入框、卡片、列表行、状态标签、弹层、对话框等，浅色 / 深色自动切换。它和第 14 节商户端 `lib/kit/` 里的组件是两个层次，下面的规则只管 `ui_kit` 的使用方式。

**总原则：组件库是实现工具，不是设计权威。** 设计稿页面是视觉依据（见 `AGENTS.md`）；不得为了用组件库的组件，去改设计稿的结构、文案、样式或交互。产品需要的多样性优先于复用。

### 17.1 后台端：强制使用

- 后台页面里的按钮、卡片、状态标签、列表行、输入框、开关、分段控件、选择标签、搜索框、横幅、页头、底部操作栏、底部弹层、对话框，一律使用 `ui_kit`，**不得在页面里新写同类控件**。后台只保留自己的页面骨架与业务展示（`lib/ui.dart` 里的 `AdPage`、`KV`、`ToneTile` 等）。
- 提交类按钮只传 `loading`，页面自己维护加载状态，不再做额外的“提交中…”处理；确认类用 `showAppDialog(onConfirm:)`。
- 颜色、字号、圆角取自令牌，页面里不写 `Color(0x…)` 去改组件外观。页面级装饰（头像渐变、深色卡上的白字等）可以保留，但新增代码优先取令牌。
- 组件库没有对应的样式时，**不在页面里覆盖**，而是给组件库补一个有语义的枚举值或参数（不开放任意颜色 / 字号），同时：补测试、在后台「我的 → 组件库」预览页里加演示、更新 `packages/ui_kit/README.md`。
- 后台设计稿与组件库画板不一致时，不得悄悄让一边迁就另一边：先列出差异（位置、设计稿写法、组件库写法），由产品确认以谁为准，再决定改设计稿实现、加组件库变体，还是接受组件库样式。不允许事后补列。
- 后台令牌 `C` 与 `AppTokens` 的取值由 `test/theme_tokens_test.dart` 保证一致，改任一边都要同步。

### 17.2 商户端：优先使用，不强制

**按钮例外（2026-11-13 用户明确批准）**：全部普通按钮、图标按钮统一采用 `AppButton` / `AppIconButton` 的标准外观、尺寸、颜色和交互，无需还原旧按钮样式；短信验证码单独使用 `AppSmsCodeButton`。这项批准取代本节按钮相关的“不批量替换 / 保留旧样式”要求；页面结构、业务文案、导航、表单字段、列表、标签、开关、选择器与业务流程仍保持。共享空态、错误重试和 Toast 的操作按钮经 `AsyncButtonTheme` 注入相同标准组件，异步包不反向依赖 UI 包。

**选择标签例外（2026-11-13 用户明确批准）**：商户普通单选 / 多选胶囊统一使用 `AppChoiceGroup` / `.multiple`，高度、文字颜色、圆角、字号、间距、按压与禁用外观采用组件库标准。会员卡种、服务分类、回访分类保持单行横向滚动；预约时段用 `kind: tile, columns: 3`，删除“原”字及专用样式，保留可用性禁用和原预约信息。允许标准标签高度与间距导致的局部布局变化；真正的分段条、复选框、会员等级及复杂业务选择卡保持原实现。业务回调、权限、异步锁和后端不随标签替换而改变。此批准优先于本节旧的标签不批量替换约定。

**分段选择例外（2026-11-13 用户明确批准）**：商户真正的分段选择统一使用 `AppSegmented`，滑块高 32、内边距 4、总高 40；颜色、阴影、圆角、字号与普通计数字色均采用组件库标准。称呼使用 `compact` 按内容宽度排列，其余等宽铺满；普通计数包含 0。用户补充批准订单保留 5 个日期选项，组件支持 2～5 项；库存动态分类改为横向 `AppChoiceGroup`。保留业务状态、回调和 TODO 阻止，重复点击当前项不触发回调。预算展示卡、充值金额/方式卡、员工角色说明卡及施工进度卡不在此批范围。此批准取代选择标签批次中“真正分段条保持原实现”的约定。

商户端有大量逐页精调的设计稿实现和约 14 万行生成页面，按下面的顺序判断，**不为了用组件库而牺牲设计稿的实现**：

1. **设计稿的写法和组件库组件完全一致**（尺寸、颜色、圆角、交互都一样）→ 使用 `ui_kit`。
2. **有差异** → 保留设计稿的实现，不为迁就组件库而改样式；颜色仍取令牌，不再新增写死色值。
3. 同一种差异在**三处以上**重复出现，说明组件库缺一种语义 → 提出新增变体，走设计确认后再加，不在页面里各自拷贝。

具体约定：
- **新页面**：优先用 `ui_kit`；设计稿里有特殊样式的部分，局部自定义。
- **既有页面**：不做批量替换。只有在改到某个页面、并且该处与组件完全一致时，才顺手替换，并验证视觉与改前一致（对照设计稿或截图），再合入。
- **历史生成页面**（`apps/merchant/lib/pages/gen/`、`gen_st/`）：按第 18 节逐页转为正式维护源码；迁移不要求批量替换为 `ui_kit`，仍以视觉一致为前提。
- 第 12、13 节的单选标签、数字增减（`HNumberStepper`）等规范继续有效，已按它们实现的页面保持不变。
- 商户端迁移前需要先补截图对比基线，否则无法证明视觉没有变化。

### 17.3 组件库本身的约定

- 定制只通过语义参数（`kind`、`size`、`tone`、文案、图标、插槽）；**不开放** `color`、`radius`、`textStyle` 这类自由样式参数（`packages/ui_kit/test/package_boundary_test.dart` 会检查）。
- 变体必须有：设计稿依据、测试、预览页演示。一次性的差异留在页面里，不进组件库。
- 组件不含业务逻辑、不请求数据，也不依赖应用或后端 SDK；空 / 加载 / 错误 / Toast 直接引用 `async_kit`，不重复实现。
- 组件库的取值来自设计稿「组件库」画板；画板之间或画板与页面设计稿冲突时，按 17.1 的方式确认，不由开发自行取舍。

## 18. 商户 App 源码维护与历史生成代码迁移

用户已明确要求进入源码迭代模式。本节取代商户 App 原先“修改设计稿或生成脚本，再生成页面”“禁止迁移生成页面”的维护方式；不代表历史代码已经完成迁移。用户另已批准删除一期不用的前端代码；一期保留业务的视觉基线及后端接入范围不变。

### 18.1 维护对象与视觉基线

- Flutter 源码是后续维护对象，设计稿作为视觉参考。新增页面直接编写 Dart；设计稿转 Flutter 的生成器、重写模式、页面派生脚本及专用辅助脚本已移除，不再生成或覆盖页面、绑定层及路由。
- 先根据真实调用链删除已被替代且无调用的重复模板及一期不用的前端代码；已实现的后端保留。对一期保留业务，允许复用现有布局，按业务批量转为普通源码；目录外的 `*_template.dart` 同样纳入迁移。
- 一期保留页面的结构、文案、样式、交互与导航保持不变；已有加载与反馈规范继续有效。删除一期不用的前端代码已统一获批，其他视觉变更仍需明确批准。迁移不附带全量组件替换、业务扩展或后端重写。

### 18.2 显式行为与状态归属

- 页面中的按钮显式绑定 `onPressed` / `onTap` 等业务回调。从页面可追踪到加载、提交、成功及失败处理；路由只负责导航，通用点击与输入组件只负责交互。
- 业务动作使用明确的方法与参数；不得根据路由名、按钮文案、placeholder、示例值或遍历控件树推断保存、删除等操作，也不得以全局导航拦截代替业务回调。
- 表单字段、校验与提交状态归当前页面或该页面持有的状态对象管理。编辑目标通过明确的数据或 ID 传入；按业务整批移除对 `CatalogDraft.current` 等全局可变编辑状态的依赖，确保不同页面实例不串数据，并释放控制器与监听。
- 简单页面可以直接调用现有接口层；复杂逻辑按业务内聚后再提取，不强制每页增加 controller / repository 等多层转发。接口层负责请求与响应，关键权限、价格、权益和状态变更仍由后端校验。
- 页面显式提供输入初值、`onChanged` 和选择结果；UI 文案仅用于展示。无数据、无权限与未登录按既有规范处理，未接通动作保留明确 TODO 并阻止操作，不引入假成功或示例数据回退。
- 继续复用统一异步组件。提交期间防重复点击，失败保留输入，成功后返回明确结果或通过既有缓存机制通知列表刷新；不依赖“跳到某个路由”间接触发保存或刷新。

### 18.3 先清重复，再按业务批量迁移，最后集中验收

1. **核对真实调用链并清理**：区分正在使用的页面、被替代的重复模板和一期不用的前端。核对导入、路由覆盖、动态入口及公共依赖，确认无调用的重复代码直接删除；一期不用的页面及专用路由、绑定、状态、资源和测试一并删除。已实现的后端保留，保留一期仍使用的公共代码，并在迁移清单记录删除依据及替代入口。
2. **按业务整批迁移**：一次处理员工、库存、会员等一整条调用链，覆盖页面、目录外绑定模板、公共组件和导航调用者。按业务组织目录，显式绑定字段、事件和结果；同时清除相应路由业务拦截、字段猜测及全局编辑草稿，更新引用和扫描范围。
3. **按变更风险验证视觉**：纯目录移动检查导入、路由和静态分析，不逐文件截图；具体布局变化比对对应页面，共享布局组件变化重点比对代表页面及受影响状态。截图使用相同数据、主题和尺寸，并等待所验证状态实际显示。
4. **每批运行相关检查**：运行受影响业务的现有测试与必要新增测试。公共组件调整完成和最终交付时再跑全量测试；出现失败或新的跨业务风险时再扩大检查范围，不每迁移一页重复全量回归。
5. **集中验收**：扫描旧目录引用、隐式字段映射、全局编辑状态、mock 回退与 TODO 假成功，结合关键流程验证。确认保留业务调用链完整、后端实现保留、旧目录无文件和引用后，移除 `gen/`、`gen_st/` 及 `st_gen/`；仅改目录名不算完成。

### 18.4 完成标准

- 打开页面源码即可找到字段绑定、加载入口、提交方法、实际接口调用及结果处理，无需到通用组件中查找隐藏业务。
- 路由只构建和打开页面；迁移页不再依赖文案识别、路由识别或全局编辑草稿。原有调用者仍可正常运行。
- 按第 18.3 节选择视觉验证范围；布局或共享组件变化验证代表页面的浅色 / 深色及相关弹层、键盘、加载状态，纯目录移动不要求重复截图。
- 按页面业务验证新增、编辑预填、保存、返回 / 取消、成功后刷新，以及请求失败保留输入、重复点击与不同实例状态隔离；有删除时验证确认、失败保留弹层和成功刷新。对关键行为补充或更新有意义的自动测试，运行相关现有检查，不能删除断言来迁就迁移。
- 变更说明列出已迁移页面、保持不变的界面、真实接通动作、仍为 TODO 的动作、清除的旧分支和实际验证结果；未验证项如实说明。
