# 会员端小程序（原生微信小程序）接入真实后端

用户批准以原生 WXML / WXSS / JS 实现会员端小程序（`apps/member-mini`），并同步接入真实后端。设计稿 `Mb*` 共 20 张画板（19 页 + 1 个弹层），视觉按设计稿还原，数据全部来自 `merchant-v1` 的 `mb_*` 接口，不保留 mock 回退。

## 后端结构：独立的 `member-v1` 云函数

会员端使用单独的 Edge Function `supabase/functions/member-v1`（`POST /functions/v1/member-v1`，`action` 以 `mb_` 开头），与商户端 `merchant-v1`、后台 `admin-v1` 分开部署；三者共享同一个数据库和迁移。

| | `merchant-v1` / `admin-v1` | `member-v1` |
| --- | --- | --- |
| 使用者 | 店主 / 运营（需 Supabase 账号） | 车主（没有 Supabase 账号） |
| 鉴权 | Supabase JWT + 会话核验 | 会员会话令牌 `x-member-token`（库里只存哈希） |
| 流量 | 少量、已知用户 | 面向公网，量大得多 |

好处：会员端的异常流量或发布问题不影响商户端收银；可单独限流、回滚；代码边界清楚（`index.ts` 入口、`portal.ts` 业务、`rules.ts` 入参规则、`wechat.ts` 微信适配、`shared.ts` 数据库客户端与响应）。

约束：
- **不跨函数目录 import**：部署包按函数目录分别拷贝。需要和商户端一致的几条规则（车牌校验、充值档位、日期校验）在 `vehicle_rules.ts` 里留了小副本，`parity.test.ts` 与 `merchant-v1` 的原实现逐项比对，任何一边单独改动都会让测试失败；`supabase/deploy/test_production.py` 也会检查运行时代码没有 import 其他函数目录。
- **预约等业务规则仍只在数据库函数里**（`save_appointment`、`appointment_slot_available`、`change_appointment`），会员端和商户端调用同一份，不会出现两套规则。
- **没有隔离密钥**：函数容器是同一个，`.env.sms` / `.env.recognition` / `.env.wechat` 对所有函数可见。拆函数带来的是独立部署、限流和回滚，不是密钥隔离；要隔离需要另起容器，不在本次范围。

## 身份与安全模型

- **会员 = 门店下以手机号识别的 `members` 记录**。同一手机号可以是多家门店的会员；小程序按“当前门店”工作，门店编号只来自扫码进入（`scene`，32 位十六进制）或本机记住的选择，服务端每次都校验“该手机号是该门店会员”，客户端传错门店只会得到 403。
- **登录 = 微信手机号授权**（设计稿：“微信授权手机号登录”）。小程序拿到两个一次性凭证（`wx.login` 的 code 与手机号授权 code）交给 `mb_login`，**由服务端向微信换取 openid 和手机号**；小程序拿不到、也不能自己上报手机号。成功后签发 256 位随机会话令牌（`x-member-token`），数据库只存 SHA-256；有效期 30 天、一天内滑动续期、每个手机号最多 5 个会话；退出登录服务端撤销。
- **服务端决定的内容**：会员身份、门店、价格与折扣、工位 / 技师（会员不能指定）、容量与营业时间（沿用 `save_appointment` / `appointment_slot_available`）、取消时限。客户端只提交“选了哪些服务、哪天几点、哪辆车”。
- 表 `member_wechat` / `member_sessions` / `member_codes` 开启 RLS 且对 `anon` / `authenticated` 无任何权限，所有函数只授权 `service_role`（`supabase/tests/member_portal.mjs` 验证）。
- 会员码为 60 秒有效的一次性随机码（只存哈希，每会员最多 5 个有效码），二维码内容 `ACM1:<20 位码>`；支持时在截屏 / 录屏中隐藏。

## 保持不变的界面

19 个页面的结构、文案、配色、圆角、阴影、间距按设计稿还原（深色会员卡、车牌样式、状态胶囊、分段标签、底部操作栏、三标签栏）。样式以设计稿像素书写（`*.px.wxss` / `*.px.wxml`），`tools/px2rpx.py` 按 750/390 转成 rpx 提交入库，CI 检查生成文件未过期。

## 真正接通的动作（`member-v1`，迁移 `202611100001_member_portal.sql`）

| 动作 | 说明 |
| --- | --- |
| `mb_login` / `mb_logout` | 微信手机号授权登录 / 撤销会话 |
| `mb_stores` / `mb_overview` | 该手机号的会员门店；首页与“我的”的概览（门店、营业状态、余额、积分、卡种、次卡数、待到店 / 施工中数量、施工中的预约） |
| `mb_services` / `mb_slots` | 服务项目（会员价由服务端按卡种折扣算）/ 某天可约时段、门店休息日与可预约天数 |
| `mb_book` | 自助预约与改约（改约在同一事务里先取消原预约再创建，失败整体回滚；请求头 `x-request-id` 幂等；待到店预约最多 5 个；车辆必须是本人本店车辆） |
| `mb_appointments` / `mb_appointment` / `mb_cancel` | 预约列表（待到店 / 已完成 / 已取消）、详情、取消（须提前 2 小时，原因为设计稿三项） |
| `mb_vehicles` / `mb_vehicle_save` | 我的爱车（含累计到店）/ 新增车辆（沿用商户端车牌校验，本店车牌唯一，最多 10 辆，默认车辆） |
| `mb_card` | 本店卡种阶梯与权益（折扣、积分倍率、生日礼、预约优先） |
| `mb_code` | 会员码 |
| `mb_orders` / `mb_order` / `mb_recharge_detail` | 消费记录（服务 / 充值 / 次卡购买，本月汇总，游标分页）、订单详情、充值明细 |
| `mb_packages` | 我的次卡与门店在会员端展示的可购买次卡 |
| `mb_recharge_options` | 充值档位与赠送（与商户端同一份规则）和线上支付是否可用 |

## 仍为 TODO（明确阻止，不返回假成功）

- **线上储值充值与购买次卡**：需要微信支付商户号（服务商进件，见 `docs/backend-integration.md`「开通微信支付」）和支付回调。预期接口 `payment_create` / `payment_callback`（验签后在事务里入账，复用 `recharge_member` / `sell_package`）。`mb_recharge` / `mb_package_buy` 现在固定返回 501「线上支付暂未开通，请到店办理」，页面原样提示；`recharge-done` 页已实现但没有入口，等支付接通后跳转。“其他金额”按钮需要设计稿里的输入界面，暂提示未开放。
- **消息通知**：需要微信订阅消息 / 短信通知渠道。`mb_notices` 返回空列表，页面显示“暂无消息”。
- **优惠券**：没有营销模块，显示“—”。
- **施工节点、照片、技师履历**：依赖员工端上报（预期 `work_progress` / `mb_progress`），见上表。
- **导航**：门店资料只有文字地址，没有经纬度（预期 `stores.latitude/longitude` 随 `mb_overview` 返回后调用 `wx.openLocation`）。
- **会员码核销**：本次只做会员端出示。店员端 / 商户端扫码识别（`ACM1:` 前缀码 -> 会员，一次性、过期校验）需要在商户端扫码页（已有 TODO）或员工端实现，预期接口 `member_code_resolve`。
- **门店小程序码**：商户端「门店二维码」页尚未接后端；生成带 `scene=<门店编号 32 位十六进制>` 的小程序码需要 `wxacode.getUnlimited`（预期商户端云函数 `store_wxacode`）。目前扫码入口由运营在微信后台手工生成，或不带门店进入（默认第一家会员门店）。
- **用户协议 / 隐私政策**：登录页只有文字，未做页面；上线前需在微信公众平台填写《用户隐私保护指引》，并补协议页面。
- **未登录体验**：非会员（手机号不在任何门店）登录后显示“您还不是任何门店的会员”，不做自助注册（会员由门店办卡）。

## 已知限制

- **手机号回收**：身份以微信验证过的手机号为准。运营商回收号码后，新机主授权同一号码会看到旧会员档案。需要门店在会员换号时及时修改会员手机号；后续可增加“换绑需门店确认”。
- **门店电话**：首页 / 预约详情的“电话”取门店资料里的联系电话（注册时默认是店主账号手机号，可在商户端门店资料修改）；上线前请门店确认该号码适合对外展示。
- **会员码**为 60 秒一次性码，但本次没有核销端，所以暂时只是出示凭证，不能代替支付。

## 部署顺序与配置

1. 执行迁移 `202611100001_member_portal.sql`，再部署 `member-v1`（缺一时小程序显示错误和重试，不回退示例数据）。`merchant-v1` / `admin-v1` 不受影响，无需重新部署。
2. 服务器 `/opt/supabase/.env.wechat` 配置 `WECHAT_MINI_APPID` / `WECHAT_MINI_SECRET`（样例 `supabase/deploy/wechat.env.example`，chmod 600，不进仓库、不进小程序）。`production.py` 已把该文件注入函数容器；**需要管理员先把更新后的 `production.py` 重新安装到服务器入口，再发布后端**：旧入口的函数白名单不认识 `member-v1`，会直接拒绝部署包（不会半途部署）。未配置时 `mb_login` 返回 501「微信登录尚未配置」。函数容器需允许出站访问 `api.weixin.qq.com`。
3. 微信公众平台：服务器域名 request 合法域名加入 `https://autocare.mymember.ltd`（需 ICP 备案的主体与小程序主体一致）；在 `apps/member-mini/project.config.json` 把 `appid` 从 `touristappid` 改成真实 AppID；填写隐私保护指引；开启手机号快速验证组件（需认证的小程序）。
4. 开发者工具导入 `apps/member-mini`，体验版自测后提审。

## 临时测试发布（上传到 my-baas-helper 日志监控小程序）

用于在真机上临时测试，不是正式发版流程。工作流 `.github/workflows/member-mini-publish.yml`（Actions → Member Mini Program Publish → Run workflow），只能手动触发，推送代码不会自动上传。

**它做什么**：先跑 `npm test`，再用 `tools/package.js` 整理出运行所需文件（排除测试、工具、样式源，把占位 AppID 换成目标 AppID），然后用 `miniprogram-ci` 上传。两种模式：

| 模式 | 效果 | 对该小程序的影响 |
| --- | --- | --- |
| `preview`（建议先用） | 生成预览二维码，在运行结果的 Artifacts 下载 `member-mini-preview-qrcode`，开发者 / 体验者微信扫码，25 分钟内有效 | 不产生版本记录，不动体验版 |
| `upload` | 上传为开发版本（机器人 30 号，版本号 `0.0.<UTC 时间>`，描述带「临时测试·勿提交审核」），再到后台手动「选为体验版」 | 增加一个开发版本；设为体验版会**替换该小程序当前的体验版** |

> ⚠️ **上传的是汽美管家会员端的整套代码，不是日志监控小程序的代码。** 目标是 `yoonzm/my-baas-helper`（member 日志监控小程序，AppID `wxdba60af414abc8db`，一个内部工具）。只要不在微信后台点「提交审核 / 发布」，它的线上版本不受影响；一旦把这个版本提审并发布，线上小程序就会被替换成本项目。默认使用 30 号机器人，避免覆盖它自己上传流程（默认 1 号）的开发版本。

**一次性配置（需要你在后台做）**

1. **上传密钥**：微信公众平台 → 开发管理 → 开发设置 →「小程序代码上传」。my-baas-helper 仓库 `key/private.wxdba60af414abc8db.key` 已有该 AppID 的密钥，把文件内容复制进 GitHub 即可，**不要提交到本仓库**。
2. **IP 白名单**：GitHub 托管运行器的出口 IP 不固定，需要在同一页面关闭上传 IP 白名单，或改用固定 IP 的自托管运行器。
3. **GitHub 密钥**：本仓库 Settings → Environments → 新建 `member-mini-test`（可勾选 Required reviewers 作为二次确认）→ 添加 Secret `MEMBER_MINI_UPLOAD_KEY`，值为密钥文件内容。
4. **request 合法域名**：开发设置里加入 `https://autocare.mymember.ltd`；或在体验版里打开「调试模式」临时绕过。
5. **后端就绪**：迁移 `202611100001_member_portal.sql` 与 `member-v1` 已部署，服务器 `/opt/supabase/.env.wechat` 填了**该 AppID**（`wxdba60af414abc8db`）的 AppID 和 AppSecret，否则登录返回 501。一个后端同一时间只能配置一个小程序，测试期间 `.env.wechat` 指向这个 AppID，原来配置的小程序登录会受影响。如果该 AppID 的 access_token 还被其他服务刷新，两边可能互相失效，需要改用微信的 `stable_token` 接口。
6. **能否用手机号授权登录**：微信的「手机号快速验证」需要小程序已完成企业认证并开通该能力；个人主体的小程序不能用，登录会一直失败。请先在该小程序后台确认。
7. **测试数据**：登录手机号必须是某家门店的会员（先在商户端办一张会员卡）。

**本地验证包内容**：`cd apps/member-mini && node tools/package.js --appid wxdba60af414abc8db --out /tmp/pkg`。

**密钥安全**：密钥只来自环境密钥，写入临时文件（0600），无论成功失败都会删除，不打印、不进仓库；输入参数都通过环境变量传给脚本，避免命令注入；AppID 格式、机器人编号、版本号都会校验。

**小程序资质**：该小程序的服务类目是工具类，与汽车美容预约、储值不符；只用于开发版 / 体验版测试，不能拿去提审。

**未验证**：真正的上传需要有效密钥和后台配置，本环境没有，所以这条流水线的上传步骤还没跑通过；已验证的是打包内容、参数校验、失败路径（无效密钥时报错、不泄露密钥、临时文件被删）和工作流语法。
