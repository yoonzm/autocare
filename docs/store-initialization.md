# 首店与分店统一初始化

注册首店与 `store_create` 均调用服务端 `initialize_store_catalog`，不再维护两套基础资料写入逻辑。界面、注册输入、创建门店导航和账号订阅名额不变。

## 默认内容

- 服务项目：按新店的主营业务，从系统默认模板筛选，与首店一致。
- 商品：同一套主营业务模板，初始库存、安全库存和成本均为 0，不创建入库/采购流水。
- 会员卡种：相同的默认名称、折扣、颜色及权益配置。
- 次卡套餐：仅初始化其包含的服务都存在的套餐，项目关联使用新门店自己的服务 ID。
- 工位：分店沿用首店的工位数量范围，生成相同的顺序命名及数量；已有工位不变。
- 营业时间：09:00–20:00 等默认预约设置；已有设置不覆盖。

不复制首店修改后的价格、现存库存、客户、余额、订单、技师或销售统计。业务类型在新增分店时沿用首店资料，基础内容使用系统模板而非首店当前经营表。

## 原子性、重试及旧店补齐

分店的门店记录、初始化资料和请求幂等记录在同一事务完成，初始化失败则全部回滚。首店注册调用相同初始化事务，失败沿用现有删除新 Auth 账号的清理逻辑。

`store_catalog_initializations` 按门店记录一次性初始化结果。锁定门店后检查记录，重试不会生成重复资料；初始化完成后用户主动删除或停用的项目不会因重试再次补回。

迁移 `202611080002_store_catalog_initialization.sql` 会对已有分店执行一次补齐：按门店和名称跳过已有服务、商品、卡种与套餐，不改价格、库存、停用/删除状态或已有套餐明细；保留现有工位和营业设置。已运营的首店不会自动重新铺默认数据，避免恢复其主动删改内容。补齐同样留下完成记录。

## 模板来源与发布

模板源为 `supabase/functions/merchant-v1/defaults.ts`。通过 `deno run tools/store_starter_snapshot.ts` 生成已发布的 `supabase/data/store_starter_v1.json`，该快照被固化在数据库迁移中。Deno 测试校验快照与 TypeScript 模板相等，数据库测试校验数据库实际快照与 JSON 相等。未来变更模板必须发布新版本和新迁移，不回写已应用的迁移，也不自动覆盖已有店铺。

模板表对客户端不可读写，初始化函数仅授予 `service_role` 执行；云函数只为刚创建、已验证归属的门店调用，不提供客户端任意门店初始化入口。

先应用新迁移，再部署云函数。迁移本身已修复原 `store_create` RPC，因此旧版门店创建接口也会获得完整默认资料。注册云函数切换到共享 RPC 后避免重复铺数据；新注册不再自行逐表插入。

## 验证

`supabase/tests/store_initialization.mjs` 在隔离 PostgreSQL 中验证首店/分店逐字段一致、旧分店有自定义数据时的补齐保留、零库存、套餐跨店关联防护、重复请求、主动删除后的重试、失败回滚与权限。`multistore.mjs` 同时回归账号订阅配额、会话切换和订阅模拟支付。测试不连接生产数据库。
