# 账号订阅与多门店

一个 `auth.users` 店主账号对应一个 `merchant_accounts` 和一份 `account_subscriptions`，拥有多家 `stores`。不新增商家主体，不强制关联营业执照或收款主体。门店的业务数据仍通过 `store_id` 独立。

## 订阅和配额

`platform_plans.store_limit` 是发布配置，`platform_plan_versions.snapshot.store_limit` 是每个订阅版本的权益。迁移默认专业版 3 家、基础版/试用版 1 家，后端版本快照决定实际限额；客户端不写死名额。暂停服务的门店仍占名额，归档不占，恢复重新校验。门店变更接口不允许客户端直接修改订阅。

`account_subscriptions` 是唯一权益来源。旧 `store_subscriptions` 保留为兼容镜像：后台从任意门店执行延期，会同步同一账号的订阅和所有门店镜像；套餐订阅人数按账号去重。`platform_orders.owner_id` 保留账号订阅订单归属，原 `store_id` 继续保留历史来源。用户后续明确批准订阅/续费暂走后端模拟支付成功；模拟订单单独标记并真实激活账号权益，不计入现金收入，见 [订阅说明](subscriptions.md)。实际支付渠道仍未连接。

降级若现有未归档门店数超限，服务端拒绝变更，要求先处理门店。`store_archive`/`store_restore` 已有接口；现有原型没有这两个操作的页面，本次不新增界面入口。为旧版本兼容，原门店不可归档；被任何登录会话选中的门店需先切走。历史业务数据不删除。

## 会话和数据隔离

`merchant_store_sessions` 绑定 Supabase 已验证登录会话 ID。没有选择记录时默认原门店，两台设备互不覆盖。`platform_merchant_session` 统一检查账号冻结、当前门店归属/归档、门店暂停以及账号订阅有效期。过期仍能读取门店列表、订阅及切换门店，业务接口拒绝操作。

新版请求带 `X-Store-Id`，业务接口拒绝与会话当前门店不一致的请求，防止切店期间旧表单写入新门店。数据库的限制性 RLS 也按当前会话门店与账号订阅过滤业务表。老版 App 的新登录会话默认访问原门店，不因为新增第二家出现 `.single()` 错误。

App 切换成功后重建主页面栈，清理会员/卡种筛选、次卡、订单、表单、扫码、挂单、服务缓存；请求代际标识丢弃切换前返回的数据，服务缓存和挂单缓存另有代际保护。存在编辑页面时切换前确认放弃表单。

## 接口

- `list_stores`：真实门店、营业额、当前门店、已用/剩余名额、创建资格、账号订阅。
- `get_subscription`：账号套餐快照及有效期。
- `store_create`：事务内锁定账号、校验有效期和配额、创建授权归属，并通过统一模板初始化服务、零库存商品、会员卡种、次卡套餐、默认营业时间和工位（工位数量范围沿用首店）；不复制经营数据。见 [初始化说明](store-initialization.md)。
- `store_switch`：校验归属，更新当前会话。
- `store_update`：修改当前门店名称、联系电话、地址，校验请求门店与当前门店一致。门店电话与账号登录手机号分离。
- `store_archive` / `store_restore`：保留历史、释放或重新检查名额。

写请求使用 `X-Request-Id`，事务内保存请求正文和结果；重放同一正文返回原结果，复用编号但改变正文会被拒绝。新增页失败保留输入及幂等编号，成功回到列表且仍停留原店。用户主动点选其他门店才切换。

## 迁移与上线

迁移 `202611070001_account_stores.sql` 保留现有门店 ID、业务数据、订阅版本和截止时间。登录手机号优先从 Auth 迁移，避免把门店联系电话误作登录身份。新增门店不会重新获得一份试用订阅。注册仍创建账号和第一家门店，账号/订阅由门店首次插入事务初始化；注册初始化失败沿用删除 Auth 账号回滚策略。

先应用数据库迁移，再部署云函数，最后发布 App。新云函数依赖新表与 RPC，不能在旧数据库上单独部署。发布前检查历史账号均有唯一有效手机号、订阅版本快照和原门店，不做猜测补订阅或延长到期时间。旧表兼容镜像保留以便旧后台报告读取，不作为第二份计费依据。

现有编辑页的门店照片/地图定位、员工登录账号授权、真实订阅支付及自动续费仍未接通；不使用本地演示门店或前端假成功兜底。

## 验证

`supabase/tests/multistore.mjs` 在本地隔离 PostgreSQL 中应用迁移，覆盖历史迁移、账号订阅共享、配额与并发创建请求、幂等重放、两设备独立切店、越权、RLS、归档恢复、后台延期、到期和权限。它不连接线上数据库。PGlite 不提供 pg_cron，测试跳过调度注册迁移，业务函数仍完整加载。

Flutter 的 `store_add_test.dart`、`store_switch_test.dart`、`store_context_test.dart` 覆盖真实请求、失败重试、表单回填、切换清理、旧响应与服务缓存迟到保护。现有页面的数据与 busy 绑定保留；原生成脚本已移除，后续按 `docs/frontend-guidelines.md` 第 18 节迁移维护，保持页面布局。
