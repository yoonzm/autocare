# 会员汇总数据库聚合

会员列表的全店汇总由 `merchant_member_summary` 在数据库中计算，不再将全店会员明细拉到云函数求和。接口仍为 `merchant-v1` 的 `kind=members, action=list`，响应字段与前端页面保持不变。

## 统计口径

- 只统计当前已验证门店的未删除会员，不受搜索、卡种筛选或分页影响。
- `total` 为会员总数；`counts` 按会员的卡种 ID 分组，不因卡种停用而漏算已有会员。
- `total_balance` 使用 PostgreSQL `numeric` 求和，不在 JavaScript 中逐笔累加。
- `new_this_month` 按北京时间本月月初（含）到下月月初（不含）计算。
- 空门店返回零值及空分组；RPC 失败或返回空结果时接口返回 500，客户端沿用现有错误与重试处理，不伪装为零余额。
- 列表的 `matched` 继续表示筛选后记录数。分页查询和汇总是两个数据库请求，并发写入时不承诺二者来自同一快照。

## 权限与部署

先应用 `202611060006_member_summary.sql`，再部署 `merchant-v1`。函数仅允许 `service_role` 执行，门店 ID 来自现有鉴权，不接受客户端指定统计门店或时间。可选 `p_at` 仅用于服务端确定性边界测试，生产调用省略，使用数据库时间。

沿用已有 `members_store_id_idx`，本次不增加索引、缓存或汇总表。后续以实际数据的执行计划决定是否增加部分索引。

## 验证与范围

`supabase/tests/member_summary.mjs` 使用隔离 PGlite 测试超过十万条记录、金额精度、跨店过滤、软删除、空门店、月初与跨年边界、数据库时区变化及调用授权，已接入开发和生产工作流。该测试使用聚合依赖的最小表结构，不替代完整迁移链和线上性能验证。

保持不变：会员页面结构、文案、样式、交互、分页筛选和响应格式；没有修改生成页面。真正接通：SQL 全店汇总及失败错误返回。无新增 mock。权限收敛与统一鉴权尚未实现，见 [待实现方案](supabase-access-hardening-plan.md)。
