# 一期 MVP 范围(限时免费、无会员端、无线上支付)

目标:不丢核心功能,先快速上线。一期只发布**商户端 App**(老板与员工同一个 App),通过收缩发布范围实现；一期不用的前端代码可直接删除，后续需要时再加，已实现的后端保留。

当前上线差距及处理顺序见文末「商户端上线差距与优先级（2026-11-16）」。该清单以现有源码和实际验证为依据，区分已确认缺陷与待验收项；历史“已接通”不等于已经达到上线标准。

## 发布范围

| 端 | 一期 |
| --- | --- |
| 商户端 Flutter App(老板 + 员工) | 上线,唯一交付物 |
| 会员端小程序 `apps/member-mini` | 不发布。`member-v1` 云函数保留,不对外承诺 |
| 店员端小程序 / 桌面端 | 不做(员工已并入商户端) |
| 运营后台 `apps/admin` | 仅内部使用:开账号、查短信、注销账号、套餐配置 |

## 一期包含

**老板侧**
- 注册 / 登录 / 忘记密码 / 账号注销(短信用助通真实渠道)
- 服务项目、会员卡种、次卡套餐、工位与营业时间、新店默认模板
- 会员与车辆、车牌扫车牌找会员
- 预约(商家代客创建、改约、取消、日程)
- 开单与收银(选择服务;会员卡、储值、次卡抵扣)
- 会员跟进、回访、挂单、反馈
- 库存:商品、入库、出库、供应商(与开单无关联:订单明细只关联服务,开单不扣库存)
- 支出:记账、分类、分摊
- 首页与基础经营统计
- 员工档案、角色、角色权限、提成方案、施工记录、停用 / 转交 / 启用

**员工侧(需独立可用)**
- 手机号验证码登录、选择身份、加入门店
- 技师:工作台、任务、更新进度、完工提交、业绩提成
- 前台:今日到店、预约、预约结算
- 权限由 `merchant-v1` 的 `staff_gate.ts` 逐请求校验

## 无线上支付的处理

- 收银只记录客户的支付方式(现金、微信收款码、支付宝、刷卡),由商家线下收款,系统只记账。
- 会员充值、办卡、买次卡同样为线下收款后录入。线上充值仍为 TODO 并明确阻止,不返回假成功。
- 不出现支付进件、收款配置、发票、退款到账等页面入口。

## 限时免费:应用内不出现任何订阅内容

一期不做订阅、套餐购买和续费。产品对用户的口径只有一句:**限时免费**。

- **注册完成页**显示"限时免费",替换原有的"专业版 · 试用至""试用结束后怎么办""看套餐"等试用与套餐文案。
- 注册即开通完整功能,没有到期时间,不做到期提醒,不进入只读模式。
- **移除应用内全部订阅入口和页面**:订阅与套餐页、确认订单、续费弹层与成功页、试用中 / 即将到期 / 已过期提示、店员"套餐已到期"页、发票、优惠券、设置与首页里的套餐信息和续费入口。
- 其他页面里出现的试用、订阅、套餐文案同步清理(例如账号注销页、条款页、更新日志)。
- **后端**:新注册账号自动开通一个内部的"限时免费"权益(完整功能、无到期)。套餐表、账号订阅表和既有同步触发器作为内部权益机制保留,不向客户端展示。商户端不再提供订阅与模拟支付入口;`subscription_catalog`、`subscription_simulate` 不对一期客户端开放。
- 员工的"套餐到期拦截"在一期不会触发,已实现的后端逻辑保留，前端到期页和专用拦截可删除。
- 以后收费时,再单独设计订阅入口、套餐与支付,并重新启用上述后端接口。这是后续单独审批的事项。
- 该方案取代原先"套餐配置里加限时免费开关"的想法,后台套餐配置本期不改。

> 用户已批准一期收缩及删除一期不用的前端代码；本节取代历史文档中“页面保留、只隐藏入口”的要求。保留的一期页面按 `docs/frontend-guidelines.md` 第 18 节批量迁移，不再重新生成。

## 商户端上线差距与优先级（2026-11-16）

审查基线：`main` / `aa1556e`，覆盖老板、店长、前台、技师共用的商户 App，以及其依赖的 `merchant-v1`、数据库迁移和发布配置。只关注生产环境和 App 构建，不排查 Supabase 开发环境。本次审查只更新文档，未修复下列业务代码或执行部署。

**结论：目前已有较完整的业务实现，但仍不满足直接公开上线的标准。** 首先处理订单数据权限、退款与账务一致性，再补齐施工、弱网重试等业务闭环，最后用同一份候选正式包完成生产验收。页面迁移完成、接口存在、历史测试通过，都不能代替这些验收。

优先级约定：

- **P0：上线阻塞。** 涉及越权、退款错误、账务错误，或目标发布渠道必需的交付条件；修复并验收后才能发布。
- **P1：一期核心完整性与稳定性。** 面向真实门店推广前完成；若要保留缺口开展小范围内测，必须明确受限路径及人工处理办法，不能默认视为已经达到公开上线标准。
- **P2：体验补齐。** 有可用替代方式、不会造成越权或错误账务，可排在核心闭环之后。
- “已确认”表示源码调用链或隔离验证已证明问题；“待验收”表示缺少当前候选包 / 生产配置的验证证据，不等于断言线上未配置。

下面的完成标准是修复建议，不扩大一期范围。实施时仍遵循视觉基线：一期不用的前端按已有批准删除；保留页面若需调整文案、交互或布局，先单独确认。

- 修复（迁移 `202611190005_order_scope.sql`、`order_scope.ts`、`orders_center.ts`）：范围由已认证会话的身份在云函数里推出（老板 / 有 `order_view_all` 看全店；只有 `order_view_own` 的员工只看派给自己的；没有对应排班资源或权限的一律 403），不接受客户端传入。本人订单 = 关联到派给该技师的预约的消费订单及其退款行；充值、次卡、没有关联预约的直接订单不在本人范围内，详情和退款越范围按“订单不存在”处理，经办人选项只给能看全店的身份。隔离测试 `supabase/tests/order_scope.sql` 复现并验证。待在生产用老板、前台、两名技师账号各验证一次。

- 现状：`staff_gate.ts` 对 `order_list`、`order_detail` 同时接受 `order_view_all` 和 `order_view_own`。但 `orders_center.ts` 只传门店 ID，`order_feed` / `order_detail` 未按当前员工限定订单；`with_options=true` 还会附带全店经办人。技师默认有 `order_view_own`，因此即使 App 不展示订单中心入口，直接调用接口仍可读取本店其他人的订单及全店汇总。这里是同店角色越权，不是已证明的跨店越权。

**P0-02 · 消费订单的未接通退款渠道仅由 App 拦截【已确认，隔离复现】**

- 现状：`OrderRefundController` 会拦住微信、支付宝、刷卡等原路退款，但 `order_refund` 后端只校验订单 ID、全额范围和原因；`refund_order` 仍可将这类订单记为已退款并返回 `back_cash`，没有真实渠道闭环。旧客户端或直接请求可绕过 App 的限制。
- 依据：[退款前端](../apps/merchant/lib/pages/orders/order_refund_controller.dart)、[订单处理器](../supabase/functions/merchant-v1/orders_center.ts)、[退款 SQL](../supabase/migrations/202611040001_order_center.sql) 的 `refund_order`。隔离数据库中，一笔微信记账订单调用该函数返回退款 100、`back_cash=100`，不涉及任何真实资金操作。
- 完成标准：云函数和事务按原订单支付构成验证允许的退款方式，缺少真实渠道的请求明确失败且不改订单、余额、次数和统计。现金线下交还、储值退回、次卡次数退回分别验证；不把收银“线下记账”的批准延伸成原路退款成功。**次卡退款接口目前已统一返回 403，不把其未触达的前端成功分支误报为已发生假退款。**

**P0-03 · 全额退款后，员工提成与业绩仍按原订单计入【已确认，隔离复现】**
