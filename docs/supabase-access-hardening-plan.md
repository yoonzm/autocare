# Supabase 权限收敛待实现方案

状态：待实现。用户决定先完成会员 SQL 汇总，权限重构暂缓。本文记录后续实施边界，不代表相关权限已经调整。

## 目标与现状

保留 Flutter → Edge Functions → 数据库的业务入口，减少普通读取使用 `service_role` 的范围，统一鉴权并建立跨店回归测试。页面、文案、导航、布局和生成页面保持不变。

目前 `supabase/functions/merchant-v1/shared.ts` 导出高权限 `admin`，普通查询和事务 RPC 都使用它。`storeFor` 通过 `userFor` 验证用户，再校验业务访问；会话状态存在重复 RPC。当前 RLS 限制客户端直接读取，但 `service_role` 绕过 RLS，云函数的门店过滤和事务函数的资源归属检查仍是关键安全边界。

本方案不扩展商家员工账号、角色授权、邀请、提成或班次。运营后台已有平台角色与商家员工权限体系分开处理。不拆分 `merchant-v1` 为大量独立函数，不将业务写入搬到客户端。

## 统一鉴权上下文

建立统一的商户请求上下文，包含经过验证的 `userId`、`sessionId`、`storeId` 及携带本次用户 JWT 的数据库客户端。建议接口为 `authorizeMerchant(request, accessMode)`，业务处理器接收上下文，不接收客户端提供的可信身份字段。

1. 验证 JWT 后才能读取并使用其中的会话信息。
2. 在一次状态查询中取得门店身份、会话有效性、冻结状态及业务访问资格，消除当前重复查询。
3. 建立明确的动作访问表：公开注册登录、已登录账号操作、营业业务操作。先盘点现有接口，保留到期后账号资料和客服入口的现有语义，避免将所有动作统一按营业资格拒绝。
4. 未声明的动作默认拒绝；请求体的 `store_id`、操作人和身份字段不能覆盖上下文。
5. 管理后台使用独立管理员上下文，验证管理员角色、会话、启用状态及具体操作权限。

## 按操作收敛数据库权限

| 操作 | 目标权限及边界 |
| --- | --- |
| 服务、卡种、会员等普通读取 | 云函数内使用用户 JWT 客户端，数据库执行 RLS；继续保留业务门店过滤 |
| 只读统计 RPC | 评估迁移为 `SECURITY INVOKER`，由 RLS 限定统计范围 |
| 充值、结算、退款、库存与预约事务 | 暂保留服务端专用 RPC，通过受控模块调用并校验资源归属 |
| Auth 账号创建与会话管理 | 独立账号模块使用高权限客户端 |
| 平台运营操作 | 独立管理通道，禁止商户上下文进入 |

普通读取切换前逐项检查主表、关联表、视图与函数。RLS 仅控制行，敏感列还需列权限或受控返回结构。直接调用 Data API 不能绕过冻结、会话撤销等已有约束。不得为了让查询通过而使用宽泛的 `using(true)` 策略。

会员汇总本轮新增的 `merchant_member_summary(uuid,timestamptz)` 仍为服务端专用 `SECURITY DEFINER` RPC，仅授予 `service_role`。后续切换为用户权限前，应验证 RLS 下的聚合语义、门店参数绑定、函数授权和查询计划，不能直接向所有登录用户开放现有高权限函数。测试时钟参数不从客户端传入。

将 `admin` 的导入限制到交易、Auth 管理及后台专用模块，并为新增违规导入建立静态检查。交易模块从可信上下文提取门店和操作人，事务内验证会员、服务、次卡、订单、库存商品、工位及技师的门店一致性。模块封装仅减少误用，不改变 `service_role` 绕过 RLS 的事实；真正的数据库最小权限需另行评估专用角色。

## 测试与验收

在隔离数据库中创建门店 A、B 及各自用户、会员、卡种、服务、订单和资源，使用真实角色及 JWT 会话上下文执行测试，不能只测试管理员查询结果。

| 场景 | 必须满足的结果 |
| --- | --- |
| A 读取 B 的列表、详情、汇总及关联数据 | 不返回 B 的信息 |
| A 对 B 的会员充值、订单退款 | 拒绝；双方余额、订单与流水均不变 |
| A 引用 B 的次卡、服务、库存或预约资源 | 拒绝，无部分写入 |
| 未登录访问业务表 | 无业务数据访问权限 |
| 普通用户调用服务端专用 RPC | 无执行权限 |
| 伪造请求中的门店或操作人 | 不改变可信身份，不越权 |
| 撤销会话、冻结账号、订阅到期 | 按动作访问表拒绝或允许，不误封账号与客服入口 |
| 商户访问管理后台或低权限管理员越权 | 拒绝，无数据变化 |

数据库测试覆盖 RLS、函数授权与事务；云函数测试覆盖路由鉴权、身份传递和错误映射。并发交易测试在真实 PostgreSQL 中运行。全部加入开发与生产 CI 门禁，并保留已有前端加载、错误重试和业务流程回归。

## 实施顺序与发布

1. 盘点动作权限表、直接数据库入口和高权限导入，先补跨店测试。
2. 引入统一上下文并合并状态查询，保持响应与状态码语义。
3. 从服务、卡种等普通读取逐模块切换用户 JWT 客户端，随后迁移会员及汇总。
