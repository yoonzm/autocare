# 后端接入标准与 V1 范围

## 运营后台

本节为用户新增批准的整个后台端接入范围，不扩展商家员工账号、邀请或提成业务。后台仍使用既有 19 个页面、导航、颜色和表单；仅登录页的演示账号提示与默认用户名按用户确认删除。生成页面未手工修改。

### 已接通与数据边界

- 运营用户名密码认证、会话恢复、强制改密、退出；角色与启用状态逐请求核验，并显式核验 `auth.sessions`，撤销后旧 JWT 无法继续使用。账号密码仅由 Auth 管理，业务表及审计不保存密码。`superman` 由服务端初始化脚本创建，随机初始密码仅创建成功后交付，首次登录必须改密，不设置公共通用密码。
- 改密兼容当前 GoTrue 的会话撤销行为：设置新密码后重新验证该密码取得新会话，再在事务中解除强制改密标记并撤销其他会话，客户端保存接口返回的新刷新令牌，不沿用已撤销的旧 JWT。
- 真实商家及统计、搜索/状态筛选、到期跟进记录、赠送七天、暂停/恢复、冻结/解冻、退出所有设备；助通代发登录验证码复用商家短信适配层及全局/手机号配额，不返回验证码。
- 平台套餐配置及版本快照、新门店试用天数、运营账号新增/启停/角色变更/随机临时密码；最后一名启用中的超级管理员不能被禁用或降级，不能禁用自己。写入与成功审计同事务；失败及越权由函数另行留痕。
- 平台订阅订单与收入使用独立 `platform_*` 模型，不混用门店会员钱包、次卡和经营订单。没有真实收款来源时，已支付列表及收入为真实空/零，不导入原型商家、订单或收入基数。历史有效试用沿用原截止时间；未知付费历史不补造订单。
- 工单查询、真实消息、回复转处理中、关闭后禁止回复；`merchant-v1` 提供 `support_list/get/create/reply`，在后端核验本店归属，提交与首条消息同事务并按请求编号幂等。商户现有“意见反馈”页接入 `support_upload/create`，保存类型、描述、联系方式和最多三张私有截图；同一内容失败重试复用请求编号和已上传截图。后台现有工单消息展示反馈元数据及截图，截图通过 `admin-v1.ticket_attachment` 鉴权后取得五分钟签名地址。商户工单列表、查看进度、查看回复、追加回复及通知仍待页面设计与后续接入，不注入演示工单。

### 云函数模块

管理端云函数按职责分模块，公开地址及 `action` 契约沿用 `admin-v1`：

| 文件 | 职责 |
| --- | --- |
| `index.ts` | HTTP 方法、JSON 边界及动作路由，统一兜底异常 |
| `shared.ts` / `types.ts` | 真实运行依赖、响应/错误映射、输入和已鉴权上下文类型 |
| `deps.ts` | 固定版本的 SDK 导入，兼容现有自托管运行时 |
| `permissions.ts` | JWT、真实会话、运营身份、强制改密及超级管理员权限检查 |
| `commands.ts` | 从请求头取得幂等编号，绑定已验证的操作人/会话，统一调用事务 RPC 和失败审计 |
| `auth.ts` | 登录、当前身份、改密后的新会话与退出 |
| `accounts.ts` | 新增运营账号及失败补偿、临时密码重置、角色和启停 |
| `merchants.ts` | 商家管控、延期、跟进及代发验证码编排 |
| `subscriptions.ts` | 套餐配置、退款动作；既有未接通渠道继续明确阻止 |
| `tickets.ts` | 工单回复与关闭 |
| `snapshot.ts` | 真实数据快照的分页读取 |
| `sms.ts` / `rules.ts` | 真实短信渠道适配、纯输入校验规则 |

新增业务动作在所属模块注册，并补齐公共权限策略与测试。关键事务和 RLS 继续由既有数据库 RPC 执行，不因代码拆分修改已部署迁移。测试通过显式注入依赖隔离 Auth/数据库/SMS，无需环境凭据或网络；生产入口只使用真实运行依赖，没有 mock 回退。

### 权限、状态与统计

`admin-v1` 使用独立运营身份表关联 Supabase Auth，验证 JWT 后读取实际会话及运营权限；注册商家身份不能成为运营。关键变更通过仅 `service_role` 可执行的事务 RPC 完成。所有新表开启 RLS，客户端没有直读/直写权限；所有现有 `store_id` 表追加限制性读取策略，已撤销会话、冻结、暂停或到期不能绕过 Edge 直接访问业务数据。账号资料接口在暂停/到期时仍可用，冻结则拒绝；解冻不恢复被撤销会话，需重新登录。

后台按 200 条分页读取各实体，全部页成功后才提交缓存，防止 REST 默认行数限制导致漏算；统计由数据库全量聚合，与当前页独立。当前使用整批分页快照保持既有列表交互，超大规模门店运营后续应改为分模块游标加载。数据刷新失败保留旧内容；写入已成功但刷新失败会说明“操作已保存”并提供重试，避免诱导重复提交。

时间统一存 UTC，按北京时间自然月/周聚合和展示。MRR 按当前付费服务周期折算；收入按确认收款日期减当期成功退款；六个月趋势动态生成并补零。续费率按上个完整自然月到期的付费周期、是否有后续付费周期覆盖到期时点计算。环比基数为零或无可计算续费样本时显示“—”。员工数显示“—”（员工模块见 docs/staff-integration.md，套餐员工名额尚未在保存时执行），不把技师数或固定数字当员工数。

### 明确保留的 TODO

- 套餐升级支付、真实付款回调、线下收款凭证确认、原路退款及对账：当前没有真实支付适配配置，对应入口明确返回未接通，不生成已支付订单、不发放付费权益、不记录成功退款。预期接口为 `payment_create` / `payment_callback` / `payment_refund` / `payment_reconcile`。
- 套餐短信通知、导出与备份、多门店权益，以及员工数上限执行：相关业务未接入，不把配置保存宣称为权益生效；当前拒绝启用三类未实现的开关。预期由各业务后端接入统一套餐授权校验。
- 注册页现有文案承诺 14 天试用，尚未接入动态公开报价文案（`public_offer`）；后端暂不允许把新门店试用期配置为少于 14 天，避免实际权益低于页面承诺。较长试用期按后端配置真实发放。
- 平台外呼、工单通知与提醒送达：缺少渠道或商家通知入口；外呼明确提示未发起，工单关闭只更新真实状态，不伪造送达。预期接口 `admin_outbound_call` / `support_notify`。

### 部署与验收

1. 先执行 `202611060004_admin_platform.sql`。迁移新增运营模型并衔接现有门店；部署前检查历史门店的套餐和截止时间，不猜测补齐付费历史。
2. 同时部署 `merchant-v1`、`admin-v1`，再发布两端客户端。后台和商家端复用 `packages/async_kit`，原商家组件路径保留 export 兼容，不复制组件实现。
   共享包只包含通用反馈能力，商户页面骨架与路由动作清单留在商户应用；两端 API 使用 `packages/supabase_adapter` 转换 SDK 异常，两端主题分别注入 `AsyncKitTheme`，不共享完整商户主题或全局亮度开关。
3. 目标环境使用仅服务端可读的 `SUPABASE_URL`、`SUPABASE_SERVICE_ROLE_KEY` 运行 `supabase/deploy/bootstrap_admin.py`，一次性生成 `superman`。已有账号时脚本拒绝覆盖；不能将输出写入仓库、迁移或流水线公开日志。
4. 私有化环境先更新 root 所有的 `supabase/deploy/production.py`，其允许列表、打包、回滚及就绪检查同时覆盖两个函数；迁移先备份，函数失败可恢复上一版本，数据库用后续迁移前向修复。Cloud 使用 `config.toml` 的公开登录配置，两端函数内自行鉴权。
5. 验证 `admin-v1` 的 Deno 类型/规则测试、`supabase/tests/admin.mjs` 的隔离 PostgreSQL 权限/事务/幂等/RLS/工单归属/分页测试、部署与初始化 Python 测试，以及后台 Flutter 分析/流程/手机深浅色回归。共享组件变动需回归商家端全套测试。真实短信冒烟不得使用现有商家号码进行自动发送。

每个接入 PR 按以上范围列出保持不变的界面、真正接通的动作及仍为 TODO 的动作；不能把本地测试通过或代码已完成写成已部署到目标环境。

## 不变的前端

设计稿及现有 Flutter 页面、导航和文案保持原样。后端接入不能重画登录页、改成邮箱表单，也不能以新的列表页替换已有服务项目或会员卡种页面。生成页面位于 `apps/merchant/lib/pages/gen/`，不要手工编辑；如现有组件缺少数据绑定，应在非生成代码的适配层接入，无法可靠接入时保留界面并标 `TODO`，不可伪称已完成。

## 加载与反馈

### 首页统计卡片

- 保持不变：营业额卡片结构、颜色、字号、七根趋势柱、快捷入口与导航。首页不再提供未登录设计预览，未登录时引导登录；统计组件只接收真实数据。
- 真正接通：登录后的今日营业额、订单数、新增会员、客单价、上周同日涨跌幅、最近七个自然日营业额，以及会员充值快捷卡片的今日充值。`home_stats` 经 Edge Function 验证登录并取得门店 ID，调用仅 `service_role` 可执行的 `merchant_home_stats`，不接受客户端指定门店或日期。
- 统计口径：北京时间自然日；营业额为已结算 `orders.payable` 之和（含余额支付，次卡抵扣后的应收，不再计入充值和售卡）；订单数包含零应收订单，排除未结算挂单；新增会员按建档时间计数（之后软删除不改写当日建档数）；客单价为营业额 / 订单数，无订单为 0；上周同日营业额为 0 时显示“—”；近七日缺数据补 0；充值只统计 `member_ledger.kind=recharge` 的 `amount`，排除赠送和其他流水。
- 加载反馈：统一 `AsyncView`、贴合卡片的骨架、失败重试、刷新保留旧值和失败 Toast；下拉刷新，以及现有业务保存成功通知后自动更新；回到前台超过五分钟刷新。切换底部 Tab 保留状态。
- 仍为 mock/TODO：订阅提醒及消息角标保持原有状态；无真实支付通道。预约入口已接入下面的预约管理接口。统计来自已记账数据，不代表支付机构到账。
- 部署：先应用 `202611030001_home_stats.sql`，再部署 `merchant-v1`；两者缺一时前端显示错误和重试，不回退示例数字。验证脚本：`supabase/tests/home_stats.sql`；前端：`test/home_stats_test.dart` 和现有首页/加载反馈回归测试。

接入后端的页面必须按 [前端规范](frontend-guidelines.md) 实现：骨架屏 / 空数据 / 错误重试 / 按钮 loading / Toast，以及统一超时、读请求重试和 401 处理。该文档末尾列出了已落地的页面和仍未做的部分。

## 后端边界

### 预约管理与资源基础资料

- **保持的界面**：预约列表、7 天日期条、状态筛选、工位时间表、新建预约、详情、改期／取消、预约设置、营业时间与工位、员工列表及工位／员工编辑表单。生成文件未改动，生成页面以非生成模板副本绑定数据；空、加载、错误与提交状态沿用统一组件。用户批准在原日期条上左右滑动切周，不增加按钮。
- **真正接通的动作**：按周查询并选择日期／状态；从本店真实会员、服务、工位和技师新建预约；读取可用时段；详情；改期；取消并释放时段；到店；带入服务开单；订单结算与预约完成在同一个事务里执行；首页待到店数量和下一位预约；预约规则及营业时间、营业日保存；工位与技师基础资料新增、编辑、停用／启用。所有写入在后端校验门店归属，RLS 只允许店主读本店数据，业务 RPC 仅 `service_role` 可执行。
- **时段规则**：北京时间；服务标准工时合计决定占用时长，不接受客户端指定时长、估价或价格。服务可在原编辑页修改工时，历史服务迁移后的默认配置为 30 分钟，应按门店实际设置。预约估价按当前服务价格和会员折扣计算，最终结算仍按收银接口计算；不预先扣次卡、余额或库存。可约时间受营业日、开始／结束时间、间隔、提前小时数和最远天数限制。同一工位、同一技师的时间区间不可重叠；相邻区间允许。全店并发上限取接待规则与实际启用工位数量中的较小值；没有工位时需先添加工位。所有创建、改期、状态变更和资源停用按门店串行加锁，防止同时抢占。
- **状态规则**：`waiting → arrived → done`，其中完成只能由关联订单成功结算触发。超过到店保留时长的 `waiting` 在读取时由后端显示为 `late`；可改期／取消，已到店／完成／取消不可改期。未来日期不能提前标记到店。取消保留记录与原因，周视图不再展示已取消预约。创建预约按 `X-Request-Id` 幂等，结算同时检查请求和预约关联，防止重复收费。
- **资源规则**：新门店开通试用时，后端按注册所选工位区间的上限初始化工位：`1–3 → 3`、`4–6 → 6`、`7–10 → 10`、`10 个以上 → 20`，名称依次为“1 号工位”等；不初始化示例员工。允许预约暂不指定资源，但仍占用全店容量；选了有固定工位的技师时，后端补齐或校验该工位；工位的默认技师也参与同样的冲突校验。有未完成预约的资源不能停用；停用工位也不得使已有预约超过剩余容量。技师列表的本月台次只统计关联该技师预约的已结算订单，不把没有技师归属的旧订单算入。
- **仍为 TODO**：会员端自助预约、待商家确认流程；微信／短信通知与提醒、通知送达记录；定金支付与退款；员工登录、邀请、角色权限、提成；个人休假／独立班次、额外节假日日期段；真实系统拨号（当前只展示真实联系电话）；预约订单挂单（调用处明确阻止，不丢弃预约关联）；无预约 ID 的字符串详情／改期深链（提示从真实预约进入）。对应控件明确提示未接通，不显示“已通知”“已收定金”或虚假送达记录。
- **部署与验证**：先应用 `202611030002_appointments.sql`，再部署 `merchant-v1`。纯输入规则见 `appointment_rules.test.ts`；SQL 事务与 RLS 断言见 `supabase/tests/appointments.sql`；前端流程见 `test/appointments_test.dart`，并回归现有首页、服务、收银和加载反馈测试。未部署接口时展示可重试错误，不回退 mock。

### 订单中心（营业记录）

- **保持的界面**：订单列表（时间页签、今日收款汇总、搜索、筛选、类型标签、按天分组）、订单详情、筛选订单、订单退款；设计稿里“今日无订单”是订单列表的一种状态，“充值订单”是订单详情的另一种版本，都不单独成页。入口：营业统计 → 营业额卡片底部“全部订单与收款”；会员消费记录里的储值充值行点进订单详情。
- **真正接通的动作**（迁移 `202611040001_order_center.sql`，云函数 `order_list` / `order_detail` / `order_refund`）：把消费、充值、次卡售卖、退款统一成一份“营业记录”，按时间倒序分页（每页 30，多取一条判断还有下一页）；时间范围今日 / 昨日 / 本周（周一起）/ 本月 / 自定义（北京时间计日，最长 366 天）；类型、收款方式、状态、经办人筛选，车牌 / 手机号 / 订单号 / 姓名搜索；订单详情；**消费订单整单退款**（`refund_order`：储值部分退回会员余额，其余记为原路退回，积分按当时赠送的扣回，累计消费和到店次数回退，次卡抵扣的次数退回；已退款不能再退，同一 `X-Request-Id` 重试返回第一次的结果）。次卡退款沿用原有的 `refund_package`，也会出现在退款里。
- **金额口径（数据库里算，客户端不算）**：实收 = 微信 + 支付宝 + 现金 + POS 刷卡，充值计入实收；**储值抵扣是会员用余额消费，不是新收的钱，不计入实收**；退款只统计真正退回支付渠道的部分（退回储值余额不算现金退款）；净收入 = 实收 − 退款，退款按退款发生当天计入，不回改原订单所在日期。汇总卡片只看时间范围，不受类型 / 收款方式 / 状态等筛选影响。订单号 = 日期 + 4 位序号（`YYYYMMDD-NNNN`，序号取自共享序列）。

- **预警与扫码**：首页、库存和商品筛选读取相同服务端标记；默认临期天数与商品单独设置生效，过期未用完批次也进入预警。扫码接真实相机，按当前门店 SKU 精确查询，也可手动输入；未找到时可携带编码新增商品。无示例商品回退。
- **边界**：App 推送/微信服务通知渠道、员工账号授权、工单完工自动扣料和负库存策略仍属于尚未接通的外部能力；对应通知开关明确阻止，不假装发送。手工出库始终禁止负库存；选择真实工单会保存关联和该单真实 FIFO 成本，不冒充自动领料。当前账号为店主，员工成本查看权限不在本次范围。
- **接口与发布**：详见 [库存实现](inventory.md)。需先应用 `202611080003_inventory_management.sql`，再发布 `merchant-v1`；此次开发使用隔离数据库验证，未连接生产数据库。
